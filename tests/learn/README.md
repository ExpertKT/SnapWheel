### ⚠️ 验证方法（这一条本身就是一个反例现场）

headless Edge 的 `--window-size` **不能把布局视口压到 504px 以下**：

```
--window-size=320  →  innerWidth 仍然是 504
```

它会**按 504px 排版，然后把截图裁到 320px**。于是"右边被切掉"看起来完全像个 bug ——
但它其实是**截图工具在骗你**。（我在同一件事上被骗了两次。）

**正确的验证办法**：在页面里套一个 `width:340px` 的容器，模拟手机宽度，再看有没有溢出。

> **教训**：「量出来的」和「看起来的」不一致时，**先怀疑你的仪器**。
> 这和 `python` 那个 0 字节占位程序是同一个形状 —— 报错信息和截图都在骗人，
> 只有换个测法才看得见真相。（反例 #10：没有测量就没有优化，只有猜测。）

## 二、工具链（已实测）

> ✅ **已修复（但值得记住案发过程）**：刚接手时这台机器上 **`python` 命令是坏的**。
>
> `python` 指向 `C:\Users\Maverick\AppData\Local\Microsoft\WindowsApps\python.exe`，
> 那是一个 **0 字节的 Microsoft Store 占位程序**（真的 `python.exe` 有一百多 KB）。
> 敲 `python xxx.py` 只会得到一句莫名其妙的
> "Python was not found; run without arguments to install from the Microsoft Store"
> —— 而 Python **其实装得好好的**，3.14.7，只是它的目录**根本不在 PATH 上**，
> 而 PATH 上排在前面的 `WindowsApps` 里蹲着一个 0 字节的假货。
>
> **怎么查出来的**：不看报错信息（它在骗你），去量**文件大小**：
> `(Get-Item ...\WindowsApps\python.exe).Length` → `0`。
> 这就是反例 #10「先测量、别猜」的最小版本 —— **报错信息说的是"没装"，
> 测量说的是"装了两个，你碰到了假的"。**
>
> **修复**：把真实 Python 目录提到**用户 PATH 最前面**（写回时保留 `ExpandString` 类型，
> 因为原值里有 `%USERPROFILE%`，展开写回去就把它写死了 —— 又一个"细节决定成败"）。
>
> **注意**：环境变量只对**新开**的进程生效。**把终端和 VS Code 全部关掉重开**，`python` 才会好用。

现在两个命令都能用：

| 用途 | 命令 |
|---|---|
| 看版本 | `python --version` 或 `py --version` |
| 跑脚本 | `python 00-toolchain-check.py` |
| 装包 | `python -m pip install <包名>` |
| 看装了什么 | `python -m pip list` |

真正的 Python：

（**3.14.7**，64 位，pip 26.2.1，`venv` 可用）

阶段 1 这段代码**只用标准库，不需要 pip 装任何东西**。虚拟环境和依赖锁定是阶段 2 的主题。

**编码小提醒**：读写文件时**显式写 `encoding="utf-8"`**。
Windows 中文环境下 Python 默认可能用 GBK 打开文件，中文会乱——这就是反例 #8（BOM）的 Python 版。

### 反例 #8 的现场版（真实发生，就发生在阶段 1 的工具里）

`stage1-predict.py` 第一版在控制台打印中文，打出来是 `��`。诊断过程：

| 实测项 | 结果 |
|---|---|
| 控制台代码页 | **936（GBK）** |
| Python 的 stdout 编码（被管道接走时） | **gbk** |
| GBK 能不能表示「第 / 题」 | **能** —— `b'\xb5\xda 1 \xcc\xe2'` |

**结论**：Python 写的是 **GBK 字节**，而读它的一方按 **UTF-8** 解释 → 乱码。

**关键认识**：这不是 Python 的错，是**「写的人」和「读的人」约定不一致**。
同一个程序，在 cp936 控制台里显示正常，在 UTF-8 终端（比如 VS Code）里就是乱码——
**它依赖环境，所以不可靠。**

**两种修法，各有取舍**：

1. 强制 `sys.stdout.reconfigure(encoding="utf-8")` —— 在 UTF-8 终端里对，在 cp936 控制台里反而坏；
2. **让控制台只输出 ASCII**（我们采用的）—— 哪种环境都不会错。

**为什么选 2**：控制台是「最小公约数」接口，**编码不是阶段 1 的学习目标**。
把精力留给引用模型。**这个取舍本身就是一次工程判断。**
