## 1. Python 速通（从 C 视角，约 2~3 周）

### 1.1 C → Python 对照表

| C | Python | 关键差别 |
|---|---|---|
| `int a[10]` | `a = [0]*10` / `list` | 可增删、可存混合类型；**有切片** `a[1:3]` |
| `struct` | `class` / `dict` / `namedtuple` / `dataclass` | 没有"按值传递"；**一切皆引用** |
| `malloc/free` | 自动 GC | 没有 `free`，但**引用还在就不会回收**（内存泄漏变成了"引用泄漏"） |
| 函数指针 | 函数是一等公民 | 直接 `f = print`；有 `lambda`、装饰器 |
| `char*` 字符串 | `str`（不可变） | 拼接用 `"".join(list)`；大量拼接用列表收集 |
| `NULL` | `None` | `None` 可以当默认值，但**别当可变默认参数**（见 §1.2） |
| 错误码 | 异常 | `try/except/finally`；`finally` 一定执行 |
| 头文件 + 声明 | 没有 | `import` 是运行时行为 |
| 缩进无所谓 | **缩进就是语法** | 混用 tab/空格会报错 |
| 编译期检查 | 运行时才报错 | 所以要**类型注解 + 静态检查**（§1.3） |

### 1.2 从 C 过来必踩的五个坑（先讲，别等他踩）

1. **可变默认参数**：`def f(x, lst=[])` —— 这个 `[]` **在整个程序生命周期里只创建一次**，会跨调用累积。正确写法 `def f(x, lst=None): lst = lst or []`。
2. **赋值不是拷贝**：`b = a`（列表）只是多一个引用，改 `b` 会改 `a`。要拷贝用 `a.copy()` 或 `copy.deepcopy(a)`。**这和 C 里"数组名是地址"有点像，但更容易被骗。**
3. **闭包里的循环变量**：`[lambda: i for i in range(3)]` 全都返回 2（延迟绑定）。要立即绑定就得用默认参数或 `functools.partial`。
4. **`is` 和 `==` 不是一回事**：`is` 比较身份（内存地址），`==` 比较值。小整数和短字符串会被缓存，导致 `is` 有时"碰巧对"。
5. **GIL**：CPython 同一时刻只有一个线程在执行 Python 字节码。**I/O 密集用线程、CPU 密集用多进程**。做 agent 时这条极其重要（大量网络等待，线程反而合适）。

### 1.3 Python 工程习惯（这部分**不要跳过**）

C 有编译器帮你把关，Python 没有，所以必须靠工具补回来：

- **类型注解 + 静态检查**：`def f(x: int) -> str:` + `mypy` / `pyright`。**这是从"能跑"到"能维护"的关键一步**，也正好补上动态类型最大的缺点。
- **虚拟环境**：`python -m venv .venv`，一人一环境，别污染系统。
- **依赖锁定**：`requirements.txt` 或 `pyproject.toml`（用 `uv` 或 `poetry`）。**记住版本，否则三个月后跑不起来。**
- **格式化与 lint**：`ruff`（一个工具全干）。别在风格上争论，让工具定。
- **测试**：`pytest`。**从第一天就写**，哪怕只测一个函数。

> **教学重点**：告诉他在 C 里"编译器"承担了多少职责，在 Python 里这些职责**必须由工具链和纪律来补**。这是语言切换最容易被忽略、后果最严重的一条。

## 2. 语言无关的工程能力（从 SnapWheel 带来的最大资产）

**这一节的所有内容是语言无关的** —— 换成 Python / TypeScript / Go 全成立。这是 SnapWheel 这个项目对他最有价值的部分。

### 2.1 反例库：我们真实踩过的 10 个坑

> 每条都是**真实记录**：有症状、有日志、有数据。

| # | 坑 | 一句话教训 |
|---|---|---|
| **1** | **度量与绘制不同源**（同一个坑摔了**四次**） | 量的时候一套参数、画的时候另一套 → 位置错位/被裁。**测量与绘制必须同源，锚点和字体必须一致；更好的做法是封装成一个函数，让错误写不出来** |
| **2** | 拿**字符串片段**当批量替换的锚点 | 片段是更大字符串的一部分 → 把它劈开了。用完整锚点，改完**必须编译/运行验证** |
| **3** | 把**复制**当成了**移动** | 语义想清楚再写代码。拖出去是复制，源就应该留着 |
| **4** | 状态用"记住原值再恢复"的方式临时保存 | **嵌套调用时状态永久丢失**（打设置窗口时又截了图）。**可嵌套的资源管理要用计数** |
| **5** | 显示值用了"当前动画值"而不是"目标值" | 数字要等动画追上去才变，看着像没反应。**区分"意图"和"呈现"** |
| **6** | 新增的绘制状态**没进缓存签名** | 画面卡在旧状态。**任何参与绘制的状态都必须进失效判据** |
| **7** | 布局按**中文宽度**估，换英文就溢出 | 文案长度不能靠字符数估。**用最长语言试一遍，宽度按实测** |
| **8** | 脚本文件编码没带 BOM | 中文全乱、语法崩。**"文件编码"是真实存在的工程细节** |
| **9** | 用**解析输出**判断成败 | 正则没转义、以及输出根本没进管道 → **连续两次把编译不过的版本推上去**。**用产物/退出码判断，不要解析给人看的输出；先验证再提交** |
| **10** | **猜着优化**（猜了三个原因、改了三轮都没对） | **没有测量就没有优化，只有猜测** —— 完整案例见 §2.4 |

**教学用法**：每条讲「症状 → 根因 → 正确做法」，然后让他在 Python 里**复现一次**（通常几行）。**第 1、4、10 条是重点**，它们代表三类不同的问题：*约定没强制*、*状态管理错误*、*方法论错误*。

### 2.2 七个技术决策（大部分语言无关）

| 决策 | 通用性 | 说明 |
|---|---|---|
| 分层缓存 + **失效签名** | ✅ 通用 | "缓存 + 明确的失效判据"是所有性能优化的基本套路 |
| **意图值 vs 当前值**分开 | ✅ 通用 | 动画、滚动、拖拽都用得上 |
| **统一坐标系** | ✅ 通用 | 多来源坐标必须归一，否则到处是转换错误 |
| **动画期间用位图，静止时用控件** | 🟡 概念通用 | 换成 Python GUI / Web 也是同一思路 |
| **平台调用集中到一个文件** | ✅ 通用 | 依赖隔离 |
| **诚实语义**（复制就是复制） | ✅ 通用 | 见反例 #3 |
| 自己画窗口/毛玻璃 | ❌ 本项目特有 | 可以跳过，或作为"技术选型的权衡"案例讲 |

### 2.4 完整案例：一次「猜了三轮 → 一测就中」的性能排查

这是反例 #10 的完整过程，**值得反复看**，它展示了正确的排查姿势。

**症状**：截图浮层里「比例」面板展开动画卡顿、不平滑。

**三轮猜测（全错）**：
1. 猜「每帧重贴整张 2560×1440 底图太贵」→ 改成只贴脏区 → **实测两者都是 0.31ms，与它无关**；
2. 猜「局部重绘能一举解决」→ 确实省了点，但仍有 13.5ms；
3. 猜「布局计算太慢」→ 实测布局函数只有 **0.07ms**。

**换成一测**（把一帧拆开，逐个绘制函数计时）：

| 分段 | 耗时 |
|---|---|
| `DrawChips`（比例胶囊整体） | **8.38 ms** ← 一半在这 |
| `PaintIntroPanel`（首次引导） | 3.30 ms |
| 工具条 / 标注 / 选区 | 均 < 1 ms |
| **全屏重绘合计** | **16.40 ms**（≈45fps，**这就是卡的原因**） |

**再细分 DrawChips**（继续问「8.38ms 花在哪」）：
- 布局计算：0.07ms ← 不是它
- 生成圆角路径 ×7：0.02ms ← 不是它
- **那 8.2ms 全在「绘制本身」** ← 反常

**再换个维度测**（小位图 vs 大位图，逐个绘制 API）：

| 操作 | 在 400×100 上 | 在 2560×1440 上 |
|---|---|---|
| `DrawString`（GDI+） | 0.035 ms | **0.015 ms** ← 不受影响 |
| **`TextRenderer.DrawText`（GDI）** | 0.431 ms | **9.229 ms** ← **慢 21 倍！** |
| `FillPath` / `DrawPath` | 0.04 ms | 0.065 ms ← 不受影响 |

**真凶**：`DrawChips` 里**只有一个** `TextRenderer.DrawText` 调用（那个 ▼ 字符），而 **GDI 的 `DrawText` 会沿着整个目标表面处理裁剪区域 —— 目标位图越大越慢**；GDI+ 的操作则与目标大小无关。

**一改成 `DrawString` 就结束**（改后实测）：

| | 改前 | 改后 |
|---|---|---|
| `DrawChips` | 8.21 ms | **0.91 ms**（9 倍） |
| `PaintOverlay` 全屏 | 16.40 ms | **13.61 ms** |

**这个案例能带走四条**：
1. **先测量**：三轮猜测全是错的，一测就中；
2. **拆开测**：测一帧不够，要拆到「每个函数、每个 API」；
3. **换维度测**：只看「代码里做了什么」会漏掉「在不同规模下差别巨大的操作」（小位图和大位图差 21 倍）；
4. **反常即线索**：当「8 个元素花 8 毫秒」这种数字明显不合理时，**里面必有某个操作在异常地贵** —— 顺着这个直觉去测，而不是继续猜。

### 2.5 完整案例：一个「改对了又被自己弄丢」的 bug

同一个功能（传递模式的"放下"）反复失败，**用户的原话是："为什么每次不能用都是一个样啊"** ——
这句话本身就是最强的线索：**如果每次失败的样子完全一致，说明我改的地方根本没碰到真正的开关。**

**真实原因只有一行**：

```csharp
// SetCursorPos 只是把光标"瞬移"过去，**不产生鼠标移动消息**。
// 而窗口的拖出是靠"按下 + 鼠标移动"启动的（OLE 拖放的启动条件），
// 收不到移动消息，DoDragDrop 永远不会被调用。
Native.SetCursorPos(x, y);
Native.mouse_event(MOUSEEVENTF_MOVE, 0, 0, 0, IntPtr.Zero);   // ← 补发"鼠标动了"这条消息
```

**而这个修复，我写过一次、又弄丢了。** 时间线：

1. 加上这几行 → 用户反馈"**重新截一张图突然就可以用了**"（其实那时它是好的）；
2. 后来为了排查另一个问题（"一进传递模式就卡死"，是我用键盘钩子搞的），**做了代码回退** ——
   这几行**被一起退掉了**；
3. 之后无论我怎么改起点坐标、改步数、改时序、改 DPI 处理，**全都得到同一个失败现象** ——
   因为那个真正的开关已经不在代码里了。

**这一条能带走四件事**：

1. **"症状一模一样"是重要信号**：它说明**改动没有触及真正的因果链**，该停下来重新找证据，
   而不是继续换着法子改；
2. **回退代码是危险操作**：回退会**连带丢掉之后的正确修复**。回退之后必须重新确认
   "当初让功能工作的那几行还在不在"；
3. **关键修复要留痕**：那几行现在带了显眼注释（`改动这段时务必保留 —— 它看起来多余，其实是关键`），
   因为**它长得像一句多余的代码**，最容易被"顺手清理掉"；
4. **先量再改仍然成立**：这次最终是靠**日志**（把"以为移到的位置"和"实际光标位置"都打出来）
   排除掉坐标因素，才把注意力拉回"移动消息"这个真正的开关上。

**同一个功能上我犯的其它错，也一并记下**：

| 错 | 教训 |
|---|---|
| 用**一次性重写整个方法**的方式改 | 把能用的逻辑整个换掉，功能直接坏 |
| 把**两次不同的反馈当成同一件事** | 用户说"目标程序没收到"，我却在修"流程跑不通" |
| 用**低级键盘钩子**去拦按键 | 它插进系统输入链，处理不当会**卡死整个系统输入**；必须回调极快、绝不 I/O、且一定卸载 |
| 用**托盘菜单上显示的文字**当作"注册成功"的证据 | 那其实是**初始值**，不是真实结果 —— 判断状态要读**运行时写下的日志**，不要读界面上的静态文字 |
| 界面布局靠**读代码猜** | 写个**离线探针**：把每个控件坐标换算到同一坐标系逐一比对，**一跑就中**（引导遮挡那个 bug 就是这么定位的） |


### 2.3 通用套路速查卡

**关于正确性**
- 量了再画，且两件事同源（#1）
- **让错误写不出来**，比"记得别写错"可靠（#1 的封装）
- 先想清语义（复制还是移动？谁拥有这块内存？）再写代码（#3）
- **状态要么完整、要么不存在** —— 半途状态最危险（#4）

**关于性能**
- **先测量，再优化**（#10）—— 最省钱的一条
- 只处理变了的那一块（脏区思维）
- 缓存 + 一个明确的失效判据（#6）
- 动画期间用位图，静止时用真实对象

**关于可维护性**
- **可嵌套的资源管理用计数**，不要"记住原值再恢复"（#4）
- 程序要能**自己说出"我哪里慢、哪里错了"** —— 日志与计时是一等功能
- 把平台相关调用集中到一处
- 构建脚本是项目的一部分，要能一键复现

**关于工作方式**
- **改完立即验证**，别攒着（#9）
- 用**产物**验证，不解析给人看的输出（#9）
- 批量替换用**完整锚点**，改完必验证（#2）
- **不确定就做个小实验** —— 比争论和猜测都快（#10）

## 3. Agent 专章（新的核心，方向性内容）

> ⚠️ **再次声明**：这一节是**公开资料与业界共识的整理**，不是第一手经验。**要带他读真实开源代码来验证**，不要只讲概念。

### 3.1 先建立正确的心智模型

**agent 的本质**，一句话：

```
agent = LLM + 工具 + 循环 + 状态
```

- **LLM**：负责"下一步做什么"的判断；
- **工具**：把判断变成真实世界的动作（查数据库、调 API、写文件）；
- **循环**：做完一步、把结果喂回去、再判断 —— **直到任务完成或达到上限**；
- **状态**：跨步骤要记住的东西（对话历史、任务进度、中间结果）。

**最容易被初学者误解的三点**（要重点纠正）：
1. **不是"让 LLM 自由发挥"** —— 生产级 agent 的关键是**约束**：工具边界、步数上限、超时、预算；
2. **不是"prompt 写好就行"** —— 大部分失败来自**上下文管理和错误处理**，不是提示词措辞；
3. **不是"一次调用就完"** —— 它是**循环**，而循环会带来所有经典的循环问题：死循环、状态漂移、错误累积。

### 3.2 Agent 特有的常见坑（业界共识，需带他验证）

> 与 §2.1 的区别：**那些是我们踩过的**，这些是**公认的**。

1. **上下文无限膨胀** —— 每轮把全部历史塞回去，成本线性涨、且后期模型会"忘记"关键早期信息。应对：摘要、只保留相关片段、结构化状态。
2. **工具调用死循环** —— 模型反复调同一个工具、或用同样参数重试。应对：步数上限、重复检测、把错误信息**原样喂回**让模型自己纠偏。
3. **错误被静默吞掉** —— 工具失败后返回空字符串，模型以为成功，继续往下走，最后给出错误答案。应对：**失败必须显式返回给模型**。
4. **不设预算和超时** —— 一次跑飞烧掉大量 token/时间。应对：**每次调用都必须有 token 上限、超时、最大步数**。
5. **prompt 注入** —— 工具返回的内容里可能藏着指令（比如网页里写着"忽略之前的指令"）。应对：区分"可信指令"与"不可信数据"，不要把工具输出直接当指令执行。
6. **非确定性导致测试困难** —— 同样的输入给出不同输出。应对：**把可确定的部分（工具、状态机、解析）与不可确定的部分（模型调用）分离**，前者写死测试、后者做行为评测。
7. **把 agent 当函数用** —— 它是带状态的长流程，需要像"服务"一样考虑可观测性（日志、追踪、每步耗时与成本）。
8. **评测缺失** —— 没有评测集就无法判断"改了 prompt 是变好还是变坏"。应对：尽早建一个**小而真实的评测集**（20~50 个真实用例）。

### 3.3 Agent 方向必学清单

| 主题 | 要掌握到什么程度 |
|---|---|
| **LLM API 基础** | 流式输出、超时重试、token 计费、错误分类 |
| **Prompt 编排** | 系统/工具/历史/用户四类消息的组织；上下文窗口管理 |
| **工具调用** | 函数签名的定义、参数校验、失败回传、**幂等性**（重试安全） |
| **Agent 循环** | 步数上限、终止条件、状态持久化（中途崩了能恢复吗） |
| **上下文与记忆** | 摘要、检索（RAG）、结构化状态 |
| **并发与重试** | 指数退避、限流、**幂等**、部分失败的处理 |
| **可观测性** | 每步的输入输出、耗时、成本；出问题能复现 |
| **评测** | 小评测集、回归（改 prompt 前后对比） |
| **协议** | **MCP**（模型与工具的标准化接口）—— 目前的事实标准，值得专门学 |

### 3.4 建议的"教材"（读真实代码）

不要只看教程。**带他读这几个开源项目**（从易到难）：

1. **MCP 的 Python SDK** —— 体量适中，直接展示"工具协议"怎么定义；
2. **OpenAI / Anthropic 官方 SDK 的示例** —— 展示最基本的循环与流式处理；
3. **LangGraph**（或类似）—— 展示"把 agent 建模成状态图"的思路，理解为什么需要显式状态机；
4. **挑一个真实的 agent 应用**（如某个开源的 coding agent）—— 看工程细节：预算控制、错误处理、日志。

**读法**：先跑通它，再找"预算控制/错误处理/状态管理"这三处代码细读 —— **不要从头读到尾**。

## 4. 学习路线（8 个阶段）

**每阶段都是「原理 → 读真实代码 → 看反例 → 自己动手 → 验收」。**

| 阶段 | 主题 | 关键产出 |
|---|---|---|
| **1** | **Python 速通（从 C 迁移）** | 能写：文件处理、HTTP 请求、JSON 解析、类与异常 |
| **2** | **Python 工程化** | 虚拟环境 + 类型注解 + 静态检查 + pytest + 一键运行脚本 |
| **3** | **第一次调用 LLM API** | 一个能流式输出、带重试与超时、能统计 token 成本的命令行小工具 |
| **4** | **工具调用与 agent 循环** | 给上一步的工具加上"能调用 2~3 个本地函数"和**步数上限** |
| **5** | **上下文与状态管理** | 让它能处理超过上下文窗口的输入（摘要或检索） |
| **6** | **读开源框架** | 能讲清 MCP 协议怎么定义工具；能改 LangGraph 的一个小功能 |
| **7** | **健壮性与评测** | 加预算/超时/可观测性；建 20 条真实用例的评测集 |
| **8** | **毕业设计** | 一个**真能用**的小 agent（自己定题），从需求到部署全流程 |

**各阶段的验收标准**（不要用"你懂了吗"结束）：
1. 能讲清**栈/堆/指针**，能写链表 → 然后能讲清 Python 里"引用 vs 值"；
2. 能**解释**为什么需要类型注解和测试（而不是背概念）；
3. 能在没有网络的情况下，**用一句话说清**这次调用的输入输出与失败可能；
4. **能画出** agent 循环的流程图，并指出三处可能死循环的地方；
5. 能算出"这次对话花了多少钱"，并说清怎么降下来；
6. 能**改一处开源代码**并让它通过测试；
7. 能拿出**评测数据**说明"我的改动让准确率从 X 变成 Y"；
8. 能完整讲一遍：为什么这么设计、最大的技术问题是什么、怎么解决的、如果重做会改哪里。

## 5. 案例：SnapWheel 还能用来教什么

虽然语言不对口、方向不对口，但它在**工程案例**上仍有价值：

| 可以用来讲 | 为什么 |
|---|---|
| **反例 #1（度量与绘制同源）** | 和"prompt 里约束与实现不一致""接口定义与实际校验不一致"是**同一类错误**：约定没强制 |
| **反例 #4（嵌套状态丢失）** | agent 的会话状态、工具调用的嵌套，会遇到一模一样的问题 |
| **反例 #10（先测量再优化）** | 优化 agent 的延迟与成本时，一模一样：**不测就不知道瓶颈在哪** |
| **`05-Err.cs`（自己报告慢在哪里）** | agent 更需要这个：每步耗时、每次调用成本、失败原因 |
| **`tools/build.ps1`（一键复现）** | agent 项目更需要可复现的构建与运行 |

**不建议**用 SnapWheel 讲：窗口绘制、DPI、拖放等平台细节 —— 与他方向无关。

## 6. 给学习对话的最后几句

1. **他的目标不是"懂某个项目"，是"敢说这是我做的"。** 所以要不断让他**自己决策、自己动手、自己解释**。
2. **多问"为什么"，少给答案。** 他想不出来了再给。
3. **反例要用真实的**（§2.1 的都是真的，有日志有数据）。编造的案例没有说服力。
4. **明确区分"我验过的"和"别人说的"**（§3 全部属于后者）—— 这本身就是最好的工程示范。
5. **每个阶段都要有能自己判断"我会了"的验收。**
6. **他每天只有 1~2 小时**，每个学习单元要能在一两天内啃完。
7. 如果他问的东西你也没把握，**直说"我不确定，我们去看代码/做个实验"**。
8. **代码只有在"能被验证"时才可信** —— 这条对 agent 尤其重要（非确定性系统更需要评测）。
