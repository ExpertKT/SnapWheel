## 0. 先读这一段：你要做什么

### 0.1 用户的背景与目标

- **编程基础**：正在学 **C 语言**，目前到「指针 / 数组 / 结构体」这一层。**没有系统学过面向对象、没有独立做过完整项目。**
- **他的真实目标（很重要）**：**不是"读懂 SnapWheel"，而是"获得独立完成一个项目的能力"**。他的原话是：*"我还是没有底气跟别人说这是我自己做的"* —— 因为他参与的是结果，不是决策。
- **所以你要教的是**：**可迁移的工程能力**（怎么组织代码、怎么设计、怎么验证、怎么排查），SnapWheel 只是**教材和案例**。
- **语言处理**：项目的代码是 **C# / WinForms**，他学的是 **C**。教学时要**用 C 的概念做锚点**：
  - 结构体 → 类
  - 函数指针 → 委托 / 事件
  - 手动 malloc/free → GC 与对象生命周期
  - 头文件 + 实现文件 → partial 类 / 多文件拆分
  - 全局变量 → 静态字段（以及它为什么危险）
- **时间投入**：**每天 1~2 小时**。意味着每个学习单元要足够小，能在一两天内啃完并留下印象。

### 0.2 他的明确要求：**不要走我们开发时走过的弯路**

这一条是本次交接的**核心**。项目开发过程中踩了大量坑（见 §4「反例库」）。**教学时不要让他自己踩一遍**，而是：

1. 先讲**正确做法**和**它为什么正确**；
2. 再展示**我们当时错在哪、症状是什么、怎么发现的**（真实日志、真实数据）；
3. 最后让他**在练习区亲手复现一次错误**（动手复现比听讲记得牢），但**不要让他把这个错误留在项目里**。

> 一句话：**弯路要让他"看见"，不要让他"走一遍"。**

## 1. 项目速览

**SnapWheel（快照轮环）** —— Windows 上的截图工具。

**一句话**：截完图不弹保存框，图直接变成屏幕角上一张缩略图（排成一段圆弧），要用的时候把缩略图拖进任何程序就发出去了。

**主流程（贯穿全项目的三条线，教学时就按这三条讲）**：

```
① 截图线：热键 → 全屏浮层 → 拖框选 → 标注/取字 → 确认
                                    ↓ 合成成一张位图
② 收纳线：位图 → 存进"轮盘"（内存里的列表）→ 屏幕角落的圆弧上排开
                                    ↓
③ 用图线：缩略图 → 拖出去（OLE 拖放）→ 目标程序收到文件或位图
```

**技术栈**：C# 5 / .NET Framework 4.0 / WinForms，**全部自绘**（没有用任何 UI 框架、没有一张图片资源），编译用 Windows 自带的 `csc.exe`，**零第三方依赖**，产物是单个约 300KB 的 exe。

**为什么这个项目适合当教材**：它是一个**完整的产品**（有构建脚本、测试、文档、发布、i18n、多语言、反馈闭环），又是一个人能看懂规模（约 2 万行、38 个源文件）。比玩具项目真实，比商业项目小。

## 3. 七个"为什么"：项目里最重要的技术决策

这些是**隐性知识** —— 代码能看出"怎么做"，但看不出"为什么"。教学时要重点讲。

### 3.1 为什么窗口要自己画，而不是用控件？

因为要**真透明**。Windows 上想要一个"只有圆弧和缩略图、其余部分完全透明"的窗口，必须用 `UpdateLayeredWindow`（分层窗口）。而分层窗口**不能承载普通 WinForms 控件** —— 控件的绘制不走分层通道。

代价：按钮、圆角、阴影、图标、文字全得自己用 GDI+ 画。**收益是视觉效果完全可控。**

### 3.2 为什么毛玻璃要自己抓屏，而不是用系统 acrylic？

两个原因：
1. 分层窗口**用不了**系统 acrylic；
2. 系统 acrylic 会给**整个窗口矩形**蒙一层灰，而我们要的是"只糊面板内部、边缘干净"。

做法：后台线程每 3.5 秒抓一次屏幕 → 盒式模糊 → **裁进面板形状**。抓屏用 `WDA_EXCLUDEFROMCAPTURE` 标记，保证**轮盘不会拍到自己**。

### 3.3 为什么要有"分层缓存 + 签名"？（性能的关键设计）

一帧如果每次都把所有矢量图形重画一遍，要 12.7ms —— 而其中"控件"占 5.5ms、"缩略图"占 6.0ms。

做法：把画面分成三层（环 / 缩略图 / 控件），**每层缓存成位图**，每帧只贴图。但贴图有个前提：**缓存必须还在生效**。于是给每层算一个 **64 位签名** —— 签名由"这一层依赖的**所有状态**"混合而成（悬停项、偏移量、缩放、颜色、可见性…）。

**规则**：**任何参与绘制的状态都必须进签名**，否则画面会"卡住不动"。
**这条规则我们踩过坑**：加了"删除后的位移过渡量"却没进签名 → 动画期间一直贴旧层。详见 §4.6。

### 3.4 为什么"偏移量"这种连续量要有两个变量？（`_offset` / `_targetOffset`）

- `_targetOffset` = **目标**（滚轮一滚就变，是"用户意图"）；
- `_offset` = **当前值**（每帧向目标靠近一小步，是"动画"）。

分开的好处：**意图立即记录、画面平滑跟上**。这是所有动画系统的基本套路（C 里做游戏循环也一样）。

**踩过的坑**：计数显示用了 `_offset`（当前值），于是"滚轮滚了但数字要等动画追上去才变"，看着像没反应。改成用 `_targetOffset` 后立刻正确。详见 §4.5。

### 3.5 为什么坐标系统一用"屏幕坐标"？（以及它带来的麻烦）

轮盘和截图浮层都要跨多显示器工作，所以内部统一用**虚拟屏幕坐标**。好处：计算一次到处能用。代价：**任何"相对某个容器的坐标"都要显式转换**，忘记转换就会出现"面板跑到副屏去了"这类 bug（我们真踩过）。

### 3.6 为什么设置窗口要"翻页用位图滑动"？

因为 WinForms 控件在翻页时**重排 + 重绘**会闪烁和掉帧。做法：翻页动画期间**把两页各渲染成位图**，滑动位图而不是滑动控件，动画结束再切回真实控件。

**这是一个通用套路**：**动画期间用位图，静止时用控件。**

### 3.7 为什么"拖出去"是 Copy 语义？

`DoDragDrop(..., DragDropEffects.Copy)` —— 目标程序拿到的是**副本**，所以环上那份**应该留着**（想再拖一次、或拖给第二个窗口都用得上）。

**踩过的坑**：代码在拖出成功后把图从环上移除了（等于当成了 Move），导致"拖一次就没了"。详见 §4.3。

## 4. 反例库：我们踩过的坑（"少走弯路"的核心）

**教学用法**：每条都有「症状 → 根因 → 正确做法」。讲完让他**在练习区复现一次**（复现很快，通常几行代码），然后记住。

### 4.1 【度量与绘制不同源】—— 这个坑我们摔了**四次**

**症状**：文字/图形的位置和它的边框、命中区域**对不上**，或者被裁掉一半。

**根因**：**测量用一套参数，绘制用另一套**。具体四次：
1. 竖版宣传图：用 `Graphics.MeasureString`（GDI+）量宽度、却用另一种方式画 → 实际更宽 → **右边缘被切**；
2. 表情面板：格子按 20pt 字号算，而 emoji 的**行高**远大于字号 → **表情被裁**；
3. 符号标注：量框用 `Microsoft YaHei UI`，画的时候用 `Segoe UI Symbol` → **两个字体的宽高不同** → 框和符号错位；同时**锚点不一致**（框按左上角、画按中心）→ 差半个字；
4. **GDI 与 GDI+ 混用**：用 `TextRenderer`（GDI）画、却期望它响应 `Graphics` 上的 `Translate/Rotate` 变换 —— **GDI 完全不理会 GDI+ 的变换**，于是预览正常、一合成到成品图符号就跑到图外。

**正确做法（教学要点）**：
- **测量和绘制必须走同一条 API 路径**（都用 GDI，或都用 GDI+）；
- **锚点（左上角 / 中心）必须在两边一致**；
- **字体必须一致**；
- 更工程化的做法：**把这四件事封装成一个函数**，让调用方**不可能**写错（这正是 0.8.0 要抽的"绘制度量层"，见 §6）。

> **这是整个反例库里最有价值的一条。** 它说明：**很多 bug 不是"写错了"，而是"约定没有强制"。** 好的设计让错误写不出来。

### 4.2 【不要用字符串片段做批量替换的锚点】

**症状**：批量改文案后，代码编译报错一片，字符串被"劈成两半"。

**根因**：把 `" 张"`、`" 行"`、`"接上 "` 这种**片段**当查找目标，而它们其实是**更大字符串的一部分**。

**正确做法**：**用完整字符串做锚点**；批量改动后**必须编译验证**；改前先看目标是否唯一。

> 这条是**工程习惯**，不是语法。可以顺势讲"为什么重构要用工具而不是正则乱替换"。

### 4.3 【语义搞错：Copy 当成 Move】

**症状**：拖出去的图**从环上消失了**，不能再拖第二次。

**根因**：拖放用的是 `DragDropEffects.Copy`（复制语义），但成功后代码把图从列表里移除了 —— 把 Copy 当成了 Move。

**正确做法**：**先想清楚这个操作的语义**（复制？移动？），再写代码；语义和实现要一致。

### 4.4 【状态用"属性"临时保存，嵌套时丢失】

**症状**：打开设置窗口，设置窗口跑到了轮盘**下面**（以为没打开）；截图界面也在下层。

**根因**：为了让轮盘"让位"，代码临时把它设为非置顶 `TopMost = false`，结束再恢复。但**多个地方嵌套**（截图时又打开设置）→ 恢复时拿到的是**中间态的 false** → **状态永久丢失**。

**正确做法**：用**计数/引用计数**（`PushSuppressTopMost()` / `PopSuppressTopMost()`），第一个进入时保存原值、最后一个离开时恢复。**这是"可嵌套资源管理"的通用模式**（C 里做锁、做引用计数也是同一个套路）。

**还有一层教训**：改这个时我**只抑制了"重新置顶"，却忘了它本来就还在顶层** —— 于是不但没修好，还创造了新 bug。**教训：改一个状态机前，先把它所有状态和转换画出来。**

### 4.5 【显示值用错变量：当前值 vs 目标值】

**症状**：滚轮滚动时，"第几张 / 共几张"的数字**不变**。

**根因**：数字用了 `_offset`（**当前动画值**，要等动画追上去才更新），而用户期望的是"滚轮一动就变" → 应该用 `_targetOffset`（**目标值**）。

**正确做法**：**区分"意图"和"呈现"**。凡是反映用户操作的显示，用目标值；凡是反映动画进度的，用当前值。

### 4.6 【新状态没进缓存签名】

**症状**：新加的动画（删除后缩略图"滑下来"）**完全不动**，或者画面卡在旧状态。

**根因**：这个项目用"层签名"决定缓存是否有效（§3.3）。**新增了一个参与绘制的状态，却没把它混进签名** → 系统以为缓存还有效 → 一直贴旧图。

**正确做法**：**任何参与绘制的状态都必须进签名**。这条要作为"改绘制代码时的检查清单"第一项。

### 4.7 【按中文宽度设计的布局，换英文就溢出】

**症状**：i18n 之后，设置窗口里的英文一行挤成一长串、被裁；轮盘空状态提示压住了环；比例按钮标签溢出。

**根因**：布局宽度是**按中文字符数**估的，英文换成同义句后长度往往增加 50%~100%。

**正确做法**：
- **不要按"字符数"算宽度**，按**实测宽度**（§4.1 的同一原则）；
- 需要换行的地方，`CheckBox` 这类控件**不会自动折行**，要在文案里手工插换行，或改用支持折行的控件；
- 文案本身要为翻译留余量（**设计时就用最长的语言试一遍**）。

### 4.8 【构建脚本的编码：BOM 不是可选项】

**症状**：改完 `build.ps1`，脚本突然报一堆语法错误、中文全变乱码。

**根因**：PowerShell 5.1 对**没有 BOM 的 UTF-8 `.ps1`** 会**按系统 ANSI（中文环境是 GBK）解释** → 中文注释和字符串全乱 → 语法崩。我用 `UTF8Encoding($false)`（不带 BOM）写文件，就把脚本写坏了。

**正确做法**：**改 `.ps1`（或任何会被"按行解析"的脚本）时，写回必须带 BOM**（`UTF8Encoding($true)`）。

> 这条很小，但**它让我把一个能跑的构建脚本搞坏了两次**，每次都靠 git 恢复。教学价值在于：**"文件编码"是一个真实存在的工程细节**，不是学术问题。

### 4.9 【不要用输出解析判断成败】

**症状**：脚本里写了"编译成功就提交"，结果**连续两次把编译不过的版本推了上去**。

**根因**：
1. 判断写成了 `$out -match '\[OK\] 完整版'` —— `[` 是**正则元字符**，匹配失败；
2. 改成 `$out.Contains(...)` 也失败 —— 因为 `build.ps1` 用 `Write-Host` 输出，**`Write-Host` 不进入管道**，`$out` 一直是空的。

**正确做法**：**用"产物是否存在且合理"来判断**（`Test-Path build\SnapWheel.exe` + 检查大小），或者**用退出码**。不要解析人类可读的输出。

**附带教训**：**先编译、再提交**。我把顺序写反了，两次把坏版本推上去。

### 4.10 【先测量，再优化】（贯穿始终的一条）

**症状**：比例面板展开动画卡顿。我**猜了三个原因**、**改了三轮**，都没解决。

**实测之后**：
- 我以为的元凶（每帧重贴整张 2560×1440 底图）实测是 **0.31ms** —— **根本无关**；
- 真正的数据是：**全屏重绘 22.2ms/帧（≈45fps）**，局部重绘降到 **13.5ms** —— 这才是"帧率低"的确切原因。

**正确做法**：
1. **先加计时，拿到分段数据**；
2. **按数据改，不按直觉改**；
3. 改完**再测一次**验证。

> 这是整个反例库的**方法论总结**：**没有测量就没有优化，只有猜测。** 我在这上面白烧了大量 token 和时间。

## 5. 学习路线（从 0 开始，用 SnapWheel 当案例）

**设计原则**：
- 从**他已经会的 C**出发，逐步引入新概念；
- 每个阶段都是「**原理 → 真实代码 → 反例 → 动手**」四步；
- 每阶段的动手练习写在 `tests/learn/`；
- 每阶段结束给他一个**能自己判断"我会了"**的小验收（不是选择题，是"你能不能不看资料讲清楚 / 写出来"）。

### 阶段 1：一个程序是怎么"活"起来的
- **原理**：程序入口、事件循环、消息、回调。C 里是 `main` + `while` + 函数指针；Windows 程序是 `WinMain` + `GetMessage` 循环 + `WndProc` 回调。
- **真实代码**：`90-App.cs` 的入口与托盘；`10-Native.cs` 如何声明系统调用。
- **反例**：无（这一阶段先建立心智模型）。
- **动手**：写一个 50 行的 Win32 风格窗口（C 或 C# 都行），能响应"点一下就换个标题"。
- **验收**：能解释"我点了按钮之后，代码是从哪一行跳到哪一行的"。

### 阶段 2：数据怎么组织（从结构体到类）
- **原理**：结构体 → 类；函数指针 → 委托/事件；`malloc/free` → GC 与生命周期；**封装**到底解决了什么问题。
- **真实代码**：`25-Store.cs`（图片容器）、`30-Wheel.cs`（多轮盘）、`27-Undo.cs`（撤销）。
- **反例**：§4.3（Copy 当成 Move —— 语义不清导致的逻辑错误）。
- **动手**：用 C 写一个"能存 N 条记录、能删、能撤销删除"的小程序（**不开源项目里的代码，自己写**）。然后对照 `25/27/30` 看它怎么做得更好。
- **验收**：能说清"为什么撤销要用引用计数而不用拷贝"。

### 阶段 3：画到屏幕上（坐标、度量、性能）
> **这是核心阶段**，SnapWheel 一半的技术含量在这里。
- **原理**：坐标系、绘制原语、双缓冲（为什么要双缓冲）、裁剪（Clip）、抗锯齿、字体度量。
- **真实代码**：`15-Gfx.cs`、`40-RoundButton.cs`（最小完整控件）、`61-WheelForm.Draw.cs`。
- **反例**：**§4.1（度量与绘制不同源，摔了四次）** + §4.7（按中文宽度算布局）。
- **动手**：写一个"自己画的按钮"，要求：悬停变色、按下变暗、文字在按钮里**真正居中**（用测量得到的尺寸算）。**写完用尺子量**（截图放大看），检查是否真的居中。
- **验收**：能讲出"为什么测量和绘制必须同源"，并举出一个会出错的例子。

### 阶段 4：交互（命中、状态、焦点）
- **原理**：命中测试（点在哪个对象上）、状态机、焦点与激活、窗口层级（Z 序）。
- **真实代码**：`64-WheelForm.Input.cs`（拖放、万能键）、`51-OverlayForm.Annotate.cs`（标注的选中/拖动/缩放）。
- **反例**：**§4.4（状态用属性临时保存，嵌套丢失）** + §4.5（当前值 vs 目标值）。
- **动手**：给阶段 3 的按钮加上：拖动、缩放、删除、撤销；再给它加一个"动画过渡"。
- **验收**：能画出（纸上）一个对象的所有状态和状态之间的转换。

### 阶段 5：让程序跑得快且不卡（性能工程）
- **原理**：帧预算（60fps = 16.7ms）、缓存、失效与签名、**测量方法**。
- **真实代码**：`66-WheelForm.Layers.cs`（层签名）、`05-Err.cs`（帧耗时统计）。
- **反例**：**§4.6（新状态没进签名）** + **§4.10（先测量再优化 —— 我猜了三轮都没对）**。
- **动手**：给自己阶段 4 的程序加一个"帧耗时打印"，然后**故意**制造一个卡顿，用数据找出原因并修掉。
- **验收**：能独立完成"测量 → 定位 → 优化 → 复测"这一整套流程。

### 阶段 6：工程化（从"能跑"到"能维护"）
- **原理**：分层与依赖方向、构建脚本、测试的价值、配置与向后兼容、i18n、发布流程。
- **真实代码**：`tools/build.ps1`、`tests/` 全部、`35-Settings.cs`（配置迁移）、`14-Lang.cs`。
- **反例**：**§4.2（片段替换）**、**§4.8（BOM）**、**§4.9（解析输出判断成败）**。
- **动手**：给自己的程序加上：一键构建脚本、3 个自动化测试、一个配置文件（且保证旧配置能读）。
- **验收**：能解释"为什么测试值得写"，并举出**你自己的代码里**一个"当初写了测试就能省下几小时"的例子。

### 阶段 7（毕业设计）：独立完成一个小工具
- 范围：`200~800` 行，**从需求到发布全流程**（自己定需求、自己设计、自己写、自己测、自己打包、写 README）。
- 建议题材：**和 SnapWheel 同类但不同**（例如"剪贴板历史"、"颜色拾取器"、"窗口置顶工具"）。
- 你的角色：**审阅者**，不写代码。只在卡住时给方向。
- **验收标准**：他能**完整讲一遍**：为什么这么分层、遇到最大的技术问题是什么、怎么解决的、如果重做会改哪里。

## 6. 一直在说的"0.8.0 重构"是什么（可以作为学习案例）

开发对话接下来要做的事（可以当作阶段 3 的真实案例来配合讲）：

1. **抽一个统一的绘制度量层**（`DrawKit`）—— 直接对应 §4.1，让"测量与绘制不同源"**在结构上不可能发生**；
2. **拆大文件** —— 把 1000+ 行的文件按职责拆开；
3. **i18n 文案集中校对** —— 把 380+ 条中英对照集中到一处。

这三件事都是**阶段 3 和阶段 6 的绝佳教材**：它们展示"**好的设计让错误写不出来**"这个核心思想。

## 7. 给学习对话的最后几句

1. **他的目标不是"懂这个项目"，是"敢说这是我做的"。** 所以要不断让他**自己决策、自己动手、自己解释**。
2. **多问"为什么"，少给答案。** 他想不出来了再给。
3. **反例要用真实的**（本文档里的都是真的，有日志有数据）。编造的案例没有说服力。
4. **每个阶段都要有"能自己判断会了"的验收**，不要用"你懂了吗"来结束。
5. **他可以随时回开发对话验收开发成果** —— 那是他的项目，他有权知道每一步。
6. 如果他问的东西你也没把握，**直说"我不确定，我们去看代码/做个实验"** —— 这本身就是最好的工程示范。
