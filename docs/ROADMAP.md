## 还欠着的事项（都不阻塞发布）

### 1. 小功能
- **Esc 取消时缩略图"飞回环上"的动画** —— 你当初的设计里提过，还没做。现在按 Esc 是直接消失。

### 2. 两条我当初"猜"出来、从未验证过的调整
- **性能预算**：环上有图时 16–33ms/帧，而当初的目标是 ≤20ms —— 需要实际量一次，看是否需要优化。
- **小按钮方位（225°→200°）和设置翻页时长（160→240ms）** —— 当时凭手感定的，没有实测验证。

### 3. 键盘钩子弃用带来的遗留
- 传递模式里 **WASD 仍会把字母打进目标窗口**（现在推荐用**方向键**，它不产生文字）。
- 低级键盘钩子（`WH_KEYBOARD_LL`）试过一次，**会把系统输入卡死**，已弃用。
  再做的话必须：回调里绝不做 I/O、带开关、单独验证。

### 4. 质量工程（最大的缺口）
- **交互层没有自动化回归测试**。现有测试覆盖的是图片 IO / 渲染 / 几何 / 拖放回调，
  而**今天所有 P0 问题（窗口层级、拖放失效、引导遮挡）全部出在交互层**。
  v0.9.2 这次用"离线探针 + 诊断日志"解决问题的做法，值得固化成常规手段。

### 5. 反例库
- 把今天这几条补进 `docs/LEARNING.md`：
  - **回退代码时弄丢了关键修复**（`MoveTo` 里那行补发移动事件），导致后续所有尝试都撞在同一个结果上；
  - **症状相同 ≠ 原因相同**：我一度把"拖放没成功"当成坐标问题、DPI 问题、权限问题反复修；
  - **界面布局问题要先"量"**（用离线探针把控件坐标换算到同一坐标系比对），不要靠读代码猜。

## 一、完成度评估

### 1.1 现状盘点

| 维度 | 现状 | 评价 |
|---|---|---|
| **功能** | 截图/标注/取字/翻译/滚动长截图/贴图/多 Wheel/撤销删除/剪贴板收纳/符号标注/另存为 | **主干功能齐全**，覆盖了"截图→用图"的完整链路 |
| **质量** | 两条产品线编译 0 警告；13 套可复跑测试（渲染 smoke、行为 37 项、拖放、几何仿真…）；性能有历史数据基线 | **在同类个人项目里属于偏上**，但测试以"离线渲染 + 逻辑"为主 |
| **文档** | README 英文为主中文附后；CHANGELOG 完整；英文发帖物料；演示 GIF | 齐了 |
| **发布** | GitHub Release（两个 zip）+ 反馈闭环 + 检查更新（仅提示） | 差"自动下载更新" |
| **i18n** | 381 条已接（托盘/设置/对话框/浮层/取字/长截图/反馈/轮盘文字），剩约 90 条是日志与诊断信息 | **够英文用户正常使用** |

### 1.2 已知问题清单（按严重度）

**P0（影响核心功能）**
- 无。今天修的三个 P0（截图不在最顶层、拖出后图消失、托盘菜单自动关）都已修复并发布。

**P1（体验明显受损）**
- **比例胶囊动画帧率仍低、不平滑** —— 已修两轮（局部重绘、绘制裁剪、GDI+ 渐隐），但仍未达标。**需要一次专门的性能剖析**（见 §6.3）。
- **i18n 中英文案会漂移** —— 380+ 条双写，长期缺少校对机制。

**P2（瑕疵）**
- 设置里部分英文长句仍可能挤出（已手工换行 10 条，未全量核查）。
- 引导页等零星中文串（拼接片段类）仍有遗漏可能。
- 剩余 90 条中文串（性能计时标签、诊断信息）保持中文 —— 这是**有意为之**，诊断信息是给作者看的。

### 1.3 结构性风险（决定"要不要重写"的关键）

1. **没有统一的绘制度量层** —— 这是**最真实的痛点**。两天里我在同一个坑里摔了四次：竖版图文字宽度、emoji 字体、符号字体+锚点、GDI/GDI+ 混用。根子都是"**量的时候用一套参数、画的时候用另一套**"。每处绘制各写各的，没有强制约束。
2. **几个超大文件** —— `75-SettingsForm.cs`（1000+ 行、104 条文案）、`61-WheelForm.Draw.cs`（45 条文案 + 大量绘制）、`50-OverlayForm.cs` + `51-OverlayForm.Annotate.cs`（浮层与标注耦合，各 1000+ 行）。绘制、命中、坐标、文案混在一起。
3. **最大的质量缺口：没有自动化交互回归测试** —— 目前只能"编译通过 + 离线渲染看图"，**交互层面的正确性完全靠人工**。这就是"改一处崩一处"的根源，也是这两天反复返工的真正代价。
4. **`Lang.T(zh, en)` 就地双写** —— 好处是漏翻一眼可见、不用维护 key 表；代价是 380 条之后中英会慢慢漂移，需要一轮集中校对。

### 1.4 结论：不建议全量重写

**理由**：
- 注释里沉淀了大量"为什么这么做"的隐性知识（分层缓存与签名的取舍、毛玻璃为什么自己抓屏、UIA 权限的坑、性能基线的由来…）。**全量重写 = 把这些知识清零**。
- 13 套测试是重要资产，重写后要重做。
- 所有历史回归要重演一遍 —— 而这两天已经证明，**这个项目改动的风险主要来自"交互与绘制的耦合"，不是来自代码难看**。

**建议：渐进重构**，只打上面列出的三个真实痛点（见 §4）。

## 四、0.8.0：渐进重构的范围

### 4.1 抽一个统一的绘制度量层（✅ 已完成 2026-09-15）

**已落地**：`src/16-DrawKit.cs` + `tests/drawkit-test.cs`（**6/6 通过**，项目第一套像素级自动化测试）

**核心约束**：`Draw` 只接受 `Measure` 返回的 `Fit` 值（字体、字号、样式都封在里面）——
调用方**拿不到单独的字号，也就没法"另起一套"去画**，让反例 #1 那个错误在结构上写不出来。

**全线 GDI+**：因为实测 GDI 的 `DrawText` 在 2560×1440 位图上单次要 9.2ms（小位图只要 0.43ms，差 21 倍）。
这也让"量与画"自然落在同一条路径上。

**测试当场逼出两个没预料到的问题**（这就是自动化测试的价值）：
1. **字号与宽度不是线性关系**（有舍入/hinting），按比例算一次仍溢出 → 改迭代缩小 + 10% 余量；
2. **缩到最小字号仍放不下**时原实现会一直溢出 → 改成逐字截断加省略号（UI 常识）。

**⚠️ 迁移策略（修正）**：**不做一次性大改**。检查后发现现有绘制点**大多本来就是 GDI+ 同源**
（例如 `69-ArcUi.ArcText` 就是 `MeasureString` + `DrawString`，没有 bug），真正的错误只有那处 `TextRenderer`（已修）。
所以 DrawKit 的价值是 **"给新代码用 + 提供统一入口"**，旧代码**按需迁移**，不为迁移而迁移。

---

### 4.1b 原始设想（留档）
新增 `src/16-DrawKit.cs`，把"量了再画"这件事变成**一个 API**，让"度量与绘制不同源"**在结构上不可能发生**：

```csharp
// 现状（危险）：各写各的，量用 A、画用 B，很容易错位
Size sz = TextRenderer.MeasureText(t, f, ...);     // GDI 量
g.DrawString(t, f, br, r, sf);                     // GDI+ 画  ← 不同源

// 重构后（安全）：量返回一个句柄，画只能用它
var fit = DrawKit.Fit(g, text, maxW, pt, fontName); // 内部保证同源
DrawKit.Text(g, fit, rect, color, TextAlign.Center);
```

**收益**：一次修掉这两天反复摔的那个坑，并且**以后不可能再犯**。
**风险**：低（新增层，不改现有行为；逐处替换并对照渲染图验证）。

### 4.2 拆大文件
- `75-SettingsForm.cs` → 按页拆成 `75a/75b/75c/75d`（每页一个 partial）；
- `50-OverlayForm.cs` + `51-Annotate.cs` → 把「标注数据模型（Shape/命中/几何）」独立成 `51a-AnnotModel.cs`，与「绘制」和「交互」分离；
- `61-WheelForm.Draw.cs` → 把「文案表」抽出来（见 4.3）。

**收益**：单文件回到可读规模；改一处不必读四千行。
**风险**：中（机械搬迁，但要逐文件验证渲染一致）。

### 4.3 i18n 校对（✅ 已完成 2026-09-15）

**做法修正**：原计划是"把所有 `Lang.T(zh,en)` 抽成一张对照表"。实测后发现**不值得** ——
`Lang.T` 就地双写已经达到目的（漏翻一眼可见、不用维护 key），抽表是**几百处的大改动**而收益不确定。

**改为**：写了一个**可复跑的检查脚本** `tools\check-i18n.ps1`，自动扫出三类问题：
1. 英文为空、或英文里还残留中文（漏翻）；
2. 同一个中文配了不同的英文（改的时候只改了一处 → 翻译漂移）；
3. 中英长度比异常（只提示，不一定错）。

**实测结果**：**427 条**，**零漏翻、零空值、零不一致**。
标出的"英文过长"都是正常的（"截图"→"Screenshot" 本来就该长）。

以后加文案，跑一次这个脚本就知道有没有漏。

## 五、自动更新（不花钱）与安装包（不做）

### 5.1 自动更新：GitHub Releases API + 自更新器

**完全免费，不需要服务器、不需要签名、不需要任何账号付费。**

```
① 启动时（或每 3 天）GET https://api.github.com/repos/ExpertKT/SnapWheel/releases/latest
   —— 匿名请求，限流 60 次/小时/IP，够用
② 比较 tag_name 与 AppInfo.Version
③ 有新版 → 托盘气泡 + 菜单出现「下载更新 vX.Y.Z」
④ 用户点击 → 下载 zip 到 %TEMP%\SnapWheel-update\
⑤ 解压 → 用 `SnapWheel.exe --apply-update <解压目录>` 启动一个**更新器模式**：
     · 等待当前进程退出
     · 覆盖 exe / 图标 / 说明文件
     · 重新启动主程序并退出自己
⑥ 失败任何一步 → 静默回退，菜单里保留「打开项目主页」手动下载
```

**要点**：
- **不需要证书**：升级是**覆盖已有文件**，不触发 SmartScreen（只有首次下载的新文件会触发，而用户是主动下载的）。
- **国内连不上 GitHub** 是常态 → 检查更新**必须静默失败**，并在设置里给一个开关（默认开）+ 手动「检查更新」菜单项。
- **绿色版可写**：程序放在用户自己的目录里，覆盖自己是允许的。若放在 `Program Files` 且无写权限 → 提示用户手动下载。
- **实现量**：约 300 行（下载 + 解压 + 更新器模式 + 命令行参数）。

**如果你以后想更省心**（可选，不是必须）：换成一个自己的静态域名放版本 JSON，代码几乎不用改（把 URL 抽成常量即可）。但**目前 GitHub 就够了**。

### 5.2 安装包：建议**不做**

| 理由 | 说明 |
|---|---|
| **与核心卖点冲突** | "一个 274KB 的 exe，双击就跑、不写注册表" 是明确写进 README 的卖点。安装包（哪怕 Inno Setup 这种轻量的）也意味着：安装目录、卸载项、开始菜单、可能写注册表 |
| **维护成本真实** | 安装包要跟着每个版本重打、要测升级路径、要处理"装了之后又拿绿色版覆盖"这类脏状态 |
| **Windows 生态已经能覆盖** | 用户想要快捷方式，自己在 exe 上右键"发送到→桌面快捷方式"即可；真想做，我可以在**设置里加一个「创建桌面快捷方式」按钮**（几十行），体验接近安装包，但不留残留 |
| **体积敏感** | 你的目标是轻量化，加安装器会让分发体积从 ~150KB 涨到 ~1MB 以上 |

**替代方案（建议）**：保持 zip 分发 + 在**首次运行引导页**里加一句"想要桌面图标？设置 → 行为 → 创建快捷方式"。成本极低，且完全符合免安装定位。

## 六、质量保障：补上最大的缺口

### 6.1 现状
13 套测试覆盖：图片 IO、渲染 smoke、行为/持久化 37 项、拖放、几何仿真、性能基准。**但交互层（点击、拖拽、键盘、焦点、窗口层级）没有自动化测试** —— 今天所有 P0 都出在这一层。

### 6.2 建议：加一套「交互回归测试」
- 用 WinForms 的 `SendMessage` / `SendInput` 驱动真实窗口（项目里 `drop-test.cs` 已有类似先例：真实 OLE 拖放 + 处理器级校验）；
- 覆盖：**截图浮层的打开/确认/取消**、**比例胶囊展开收起**、**托盘菜单**、**窗口层级断言（`GetWindow` 的 Z 序）**、**键盘路径**；
- 运行方式：`build.ps1 -Test` 里可选跑（因为它会动鼠标）。
- **收益**：今天那几个"改一处崩一处"的 bug，如果当时有这套测试，**在提交前就会被拦住**。

### 6.3 比例动画的性能剖析（专项）
现在的做法是"猜 + 改 + 看效果"，已经改了三轮仍未达标。**下一轮改成测量**：
1. 用项目里已有的分段计时机制（`05-Err.cs` 有帧耗时统计），给 `PaintOverlay` 加细粒度计时；
2. 量出"一帧里画了什么、各花多久"（底图贴图 / 选区 / 标注 / 工具条 / 胶囊）；
3. 按数据优化，而不是继续猜。

### 7.1 原始设计（你的方案，留档）

你的设想很完整，我把它整理成可实现的规格：

```
【阶段 1｜选中】键盘选中一张缩略图（方向键 / 数字键）
【阶段 2｜进入传递模式】
     · 缩略图"提起"（轻微放大 + 阴影），屏幕出现提示条
     · 允许用户自己切屏 / 切窗口（Alt+Tab、鼠标点都行）
【阶段 3｜模拟拖拽】
     · 出现**假光标**（一个小窗口，画一个光标图标，并吸附着缩略图）
     · WASD（或方向键）操控移动，速度可调（Shift = 加速）
     · 按 Esc 取消，缩略图飞回环上
【阶段 4｜落下】
     · 按 Enter / 空格 = 放下
     · 实现方式：把真实光标移到假光标位置 → `mouse_event` 模拟按下/移动/松开
       （这样目标程序会当成一次真正的拖放，兼容性最好）
     · 完成后假光标消失，缩略图按设置决定是否留在环上
```

**技术可行性**：✅ 可行。需要三个新部件：
1. **假光标窗口**（透明置顶小窗，画光标 + 缩略图）；
2. **全局键盘捕获**（传递模式期间用低级键盘钩子 `WH_KEYBOARD_LL`，或注册一组热键）；
3. **拖放模拟**（`SetCursorPos` + `mouse_event`，注意要有"按下 → 分步移动 → 松开"的过程，否则目标程序不认）。

**风险与对策**：
- **假光标与真光标不同步** → 落下时把真光标瞬移到假光标位置（用户会看到光标跳一下，可接受）；
- **目标程序需要真实的拖放过程** → 分步移动（每步 10~20ms），模拟人手速度；
- **管理员窗口收不到** → 与现有拖拽的限制一致（UIA/UIPI），提示用户即可。
