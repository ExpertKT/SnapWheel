### 1. ✅ 空转时的白干活（2026-09-19 已修）—— **过程和结果都值得记**

**结果**：空转帧率 **45fps → 7.1fps**（关掉玻璃定时刷新 22.8 → 4.5）。新增测试 `idle-frames.cs` 盯着它。

**线索**：`error.log` 最近 92 条帧统计里 **49 条平均 >20ms**，而状态全是
**`图=0`、`hover=-1`、没在动画** —— 空转、什么都没干的时候一帧平均 12ms、最慢 72ms。

**⚠️ 我猜错了两次，两次都记在这里，免得以后有人（包括我）再走一遍：**

**第一次猜：玻璃底每 3.5 秒重抓屏幕。**
代码注释自己写着"抓屏+模糊要几十毫秒"，数字也对得上。于是写了个"先采几个 12×12 的小块，
判断桌面变了没有，没变就跳过整屏抓取"。**量出来是反的**：

| | 单次耗时 |
|---|---|
| `CopyFromScreen` 12×12 | **16.7 ms** |
| `CopyFromScreen` 256×256 | 17.1 ms |
| `CopyFromScreen` 整屏 | 44.6 ms |
| 裸 GDI `BitBlt` 12×12 | 16.8 ms |

**抓屏是「按次」计费的固定成本，跟抓多大几乎无关。** 采四块反而比整屏还贵。
方案当场作废，代码已撤掉。**这个数字以后还有用：任何时候想"抓一小块就够了"，先想起它。**

**第二次猜：主题色过渡收敛不了。**
`_accentCur` 每帧靠近 `want` 22% 再 `Round` 成整数 —— 只差 1 时 `Round(cur+0.22)` 还是 `cur`，
**永远停在差 1 的地方**，于是 `_accentCur != want` 恒成立。这是**真 bug，已修**
（每通道差 ≤1 就吸附过去）。但它不是主因 —— 修完帧率纹丝不动。

**第三次才对：直接问程序"谁在要帧"。**
往 `62-WheelForm.Anim.cs` 里每个 `need = true` 后面插一行记下行号，跑一遍，答案是：

```
if (_nubHintT > 0.01f) need = true;      // 悬停期间保持刷新
if (_nubHov   > 0.01f) need = true;
if (_keyHov   > 0.01f) need = true;
```

**这三行的意思是"只要它亮着就一直重画"** —— 而提示/光晕**已经完全显示、一个像素都不再变**了。
它们是纯标量（不跟光标位置走），所以稳定之后根本没有要刷新的东西。
三行删掉（值在变化时本来就已经在请求帧了，`else if` 里还会吸附到位）→ **45fps 掉到 7fps**。

**剩余的 7fps 是玻璃定时刷新的交叉淡入**（每 3.5 秒一次、每次 0.38 秒），那是真功能，
可以通过设置里关掉「玻璃定时刷新」去掉。

### 1b. ✅ 轮盘底下悬着一条缝（任务栏自动隐藏）—— v0.9.11 已修

**现象**：任务栏设成自动隐藏之后，轮盘贴不到屏幕底边，底下永远空一条。

**原因不是"没靠边"，是 Windows 的定义**：**工作区（WorkingArea）总是把任务栏那一条扣掉**，
哪怕任务栏根本看不见。本机实测 `Bounds 1707×1067` / `WorkingArea 1707×1019` ——
底下那 **48px** 明明鼠标一碰才冒出来，工作区就是不给。轮盘是贴着工作区摆的，于是差了这一条。

**修法**：新增设置「轮盘靠边方式」（第 1 页），默认 **自动**：

| 档位 | 行为 |
|---|---|
| **自动**（默认） | 工作区确实被扣了一块 **且** 任务栏正处于自动隐藏 → 贴屏幕物理边；否则贴工作区边 |
| 贴屏幕边 | 永远贴屏幕物理边（任务栏不自动隐藏时会被压住一角） |
| 贴工作区边 | 永远避让任务栏（= 老行为，给不喜欢"偶尔被压住"的人留的退路） |

**"任务栏是不是自动隐藏"是问系统的**：`SHAppBarMessage(ABM_GETSTATE)` 的 `ABS_AUTOHIDE` 位
（`src/10-Native.cs`）。判断本身抽成了纯函数 `Native.AnchorIsScreen(mode, reserved, autohide)` ——
**真实任务栏状态测不了，但"三档 × 四种环境"这六种组合能全测**，见 `tests/edge-anchor-test.cs`（17 项）。

### 1c. ⚠️ 设置窗口打开要 250ms（**已定位，还没修**）

**现象**（用户报）：点设置按钮后窗口出现较慢，而且期间没有任何东西缓解"加载感"。

**已经量的**（2026-09-20）：

| 环节 | 耗时 |
|---|---|
| `new SettingsForm()` 合计 | **250ms**（稳定复现，预热后一样） |
| 建 root / 标题 / 分页器 / 四页格 / 六个圆按钮 / 页脚 | 全部 **0~10ms** |
| **`ShowPage(0)`** | **~220ms** |
| 尾部（挂树 + `SizeToContent`） | ~60ms |

再往里拆 `ShowPage(0)`：**`BuildPage1` 里 19 个 `Controls.Add` 全部只用 10ms**，
**贵的是建完之后的第一次布局/测量（~200ms）**。

**佐证**：对已经布局好的页面单独量 `GetPreferredSize` 只要 **2~3ms**、`PerformLayout` **3ms**；
第 2/3/4 页"建 + 排 + 量"全套只要 **8~15ms**。也就是说**只有第 1 页的第一次布局这么贵**。

**下一步怎么查**（已经排除的别再走一遍）：
- ❌ 不是 JIT（预热过一次，第二轮一样慢）
- ❌ 不是"构造过程中被重复布局"（加 `SuspendLayout`/`ResumeLayout` 后 264→270ms，**没用，已撤**）
- ❌ 不是控件建得慢（19 个 Add 只要 10ms）
- ❌ 不是"量尺寸"本身（已布局的页只要 2~3ms）
- ➡️ 剩下最可疑的：`BuildPage` 里 `_pages[0].ResumeLayout(true)` 那一下触发的**首次自动布局**。
  第 1 页是**两列 AutoSize × 10 行 AutoSize**、每格里套一个 `RowPanel`（FlowLayoutPanel，
  `WrapContents=false`，且覆写了 `GetPreferredSize` 逐个子控件取 `Bottom`）。
  TableLayoutPanel 的 AutoSize 本来就慢，这种嵌套在首次布局时要反复迭代。

**打算试的方向**（都要先量、再改）：
1. 把第 1 页的两列 AutoSize 改成固定百分比 —— 但要先确认布局结果不变（`ui-probe` 有控件重叠检查兜着）
2. 或者让 `RowPanel.GetPreferredSize` 不再逐子控件取 `Bottom`，改用 `DisplayRectangle`
3. 实在降不下来，就**把窗口先显示出来再建页**（用户看到的等待从 250ms 降到 ~40ms，
   代价是窗口出现后会自己长一下）

**已经做的缓解**：窗口从 `Opacity=0.34` 渐变到 1（约 90ms），"出现"那一下不再是硬切。

### 2b. 满环（50 张）性能 —— ✅ 已量（2026-09-19）

**为什么补这一条**：上面那份 931 条真实样本**全是环上 1~3 张图**的状态（用户当时的实际用量），
而 `MaxCount` 默认 50。满环是什么样从来没量过 —— 这不是已知短板，是**未知**，
未知比短板更该先清。工具：`tests/full-wheel-perf.cs`（已进标准套件）。

50 张 1920×1080，每态 120 帧取后 80 帧：

| 状态 | 平均 | p50 | p95 | 最慢 |
|---|---|---|---|---|
| 冷启动第一帧（现生成 50 张缩略图） | **112 ms**（一次性） | | | |
| 稳态（无悬停） | 3.06 | 2.97 | 4.34 | 4.98 |
| 悬停一张 | 2.66 | 2.68 | 3.31 | 3.52 |
| 长按放大 peek | 2.73 | 2.64 | 3.85 | 4.85 |
| 滚动中（**未预热**） | 9.76 | 7.22 | **24.31** | 26.01 |
| 滚动中（先滚一轮预热后） | 7.13 | 6.48 | **9.39** | 27.15 |

**结论：满环稳态没问题（3ms，预算 20ms）。滚动有两个已知来源**：

1. **缩略图是懒生成的**：新图第一次滚进视野时才现生成，那几帧到 24~26ms。
   先滚一整轮预热后 p95 从 24.31 掉到 9.39 —— **这印证了来源就是它**。
   可改进方向：加分后**后台预生成**缩略图，别等滚动时现做。
2. 预热后仍有一个 27ms 的单帧离群值，疑似 GC / 缓存清理（`ScaledThumb` 里 `d.Count > 200` 会清掉除最大那张以外的全部）。

两条都**不阻塞**（平均在预算内，只有极少数帧越线），但都是真原因，不是猜测。

### 4. 质量工程 —— 🟢 三件事已做（2026-09-19）

**① 诊断模式**（托盘右键 →「诊断模式（显示元素名）」）

轮盘上每个元素都画出**自己的名字和边框**，鼠标停在哪那个就高亮。
打开的截图发过来，"你指的是哪个元素"就不用再猜了 ——
这个项目为"报同一个现象三次、我修错两次"付过学费。

实现上有一条是刻意的：**名字和矩形是元素在画自己的时候顺手记下来的**，
不是另写一份几何去推算 —— 后者迟早和真实绘制对不上（反例 #1）。

**② 满环性能量过了** —— 见上面 §2b。

**③ 标注补上「重做」**

`Ctrl+Y` / `Ctrl+Shift+Z`，工具条上也有按钮（撤销图标左右镜像）。
规则和所有编辑器一样：**提交新图元就清空重做栈**。
两条边界写进了测试：撤销后提交新图元，旧的重做项不许被复活；
撤销时**不能**释放马赛克的 Cache 位图（否则重做出来是一片空白）。

### 5b. CI：从"永远绿"到真的会说话（2026-09-20）

仓库 9/13 就有 CI（`ci.yml`），但它**从建立起就是绿的** —— 因为 `build.ps1` 在测试
失败时仍然返回 0，CI 只看退出码，于是永远看不到红。这和"自动更新入口被注释吞掉"
是同一个形状：**编译通过、0 警告、测试全绿，而功能是死的。**

修掉退出码之后第一次真跑，CI 立刻报了三条 —— 对比 v0.9.9 那次（标着 success）的日志，
**同样的三条当时就在失败**。三条都只在"屏幕比本机小"时出现（本机 1067 高，runner 是 1024×768）：

| 失败 | 根因 |
|---|---|
| 浮层比例胶囊压住工具条 | 屏幕矮时工具栏只能摆"选区上方"，而胶囊往"选区上方"挪的那步**没有重新检查工具栏**，绕一圈又撞回去 |
| 轮盘手动缩放档在小屏上被裁 | "装不下就缩一档"以前**只在自动档生效**，手动设 250% 时窗口被屏幕顶住、内容没缩 |
| 取字 14px 中文小字准确率 20% | **不是 bug**：runner 只有英文 OCR 包。测试只查了"有没有 OCR"，没查"认不认中文" |

前两条修好后都抽成了**纯函数**（`OverlayForm.ChipRowY` / `WheelForm.ResolveUiK`），
测试用**假屏幕**直接算 —— 于是本机就能跑出小屏幕的结果。
负向验证时逐字节复现了 CI 的数字（胶囊 `{450,338}` vs 工具条 `{290,356,726,42}`）。

**这条经验值得记住**：一个只在**别人机器上**失败的检查，等于把"没测过"伪装成"测过了"。
把环境变成参数，它才真的在测。

### 6. 界面探针（`ui-probe`）

**新增 `tests/ui-probe.cs`：界面布局探针。**

它专门测"布局"，不测逻辑 —— 因为**这个项目里最难查的问题几乎全是"两个控件重叠"**：
引导正文压住底部按钮、比例胶囊展开压住工具条。这类问题**读代码很难发现**
（要同时把两边的位置、尺寸、坐标系都在脑子里算一遍），但**用程序量一遍就一目了然**。

做法：把每个子控件矩形**统一换算到窗口坐标系**，再两两求交。

**当前覆盖（12 项，全部通过，且已进标准测试套件）**：
- 引导 × 三种模式（设置里 / 首次 / 升级）：内容不压住底部按钮、窗口高度 ≤ 屏幕 80%（6 项）。
- 引导的【新】标记：看过当前版本 → 0 条；0.9.4 → 1 条；0.8.0 → 3 条；
  越老越多（单调）；全新安装 0 条（5 项）。
- 浮层的「比例胶囊 vs 工具条」：不重叠（1 项）。

> **v0.9.5 起 `ui-probe` 进了标准套件。** 在那之前它只能手动跑 ——
> 于是它写的断言等于没写。**一个不在流水线里的测试，和没有测试是一回事。**

**尚未覆盖 / 待补**：
- 设置窗口四页的控件边界、轮盘缩略图是否超出窗口。
- **浮层那一项曾经是空的**：探针里调 `PlaceChips` 时工具条还没布局（`_toolRect` 为空），
  于是它每次都打印"跳过重叠检查"却算作通过。**名字在、实际不测的检查比没有更危险** ——
  和"自动更新"、"【新】标记"是同一个形状。v0.9.5 已让它先跑一遍工具条布局再比。

**仍然存在的缺口**：**真正的"交互"（点击、拖放、键盘、窗口层级）没有自动化测试**。
今天所有 P0（窗口层级、拖放失效）都出在这一层，而探针和日志只能事后定位、不能提前拦住。

### 1.2 已知问题清单（按严重度）

**P0（影响核心功能）**

### 1.3 结构性风险（决定"要不要重写"的关键）

1. **没有统一的绘制度量层** —— 这是**最真实的痛点**。两天里我在同一个坑里摔了四次：竖版图文字宽度、emoji 字体、符号字体+锚点、GDI/GDI+ 混用。根子都是"**量的时候用一套参数、画的时候用另一套**"。每处绘制各写各的，没有强制约束。
2. **几个超大文件** —— `75-SettingsForm.cs`（1000+ 行、104 条文案）、`61-WheelForm.Draw.cs`（45 条文案 + 大量绘制）、`50-OverlayForm.cs` + `51-OverlayForm.Annotate.cs`（浮层与标注耦合，各 1000+ 行）。绘制、命中、坐标、文案混在一起。
3. **最大的质量缺口：没有自动化交互回归测试** —— 目前只能"编译通过 + 离线渲染看图"，**交互层面的正确性完全靠人工**。这就是"改一处崩一处"的根源，也是这两天反复返工的真正代价。
4. **`Lang.T(zh, en)` 就地双写** —— 好处是漏翻一眼可见、不用维护 key 表；代价是 380 条之后中英会慢慢漂移，需要一轮集中校对。

### 1.4 结论：不建议全量重写

**理由**：
- 注释里沉淀了大量"为什么这么做"的隐性知识（分层缓存与签名的取舍、毛玻璃为什么自己抓屏、UIA 权限的坑、性能基线的由来…）。**全量重写 = 把这些知识清零**。
- 13 套测试是重要资产，重写后要重做。
- 所有历史回归要重演一遍 —— 而这两天已经证明，**这个项目改动的风险主要来自"交互与绘制的耦合"，不是来自代码难看**。

**建议：渐进重构**，只打上面列出的三个真实痛点（见 §4）。

## 四、0.8.0：渐进重构的范围

### 4.1 抽一个统一的绘制度量层（✅ 已完成 2026-09-15）

**已落地**：`src/16-DrawKit.cs` + `tests/drawkit-test.cs`（**6/6 通过**，项目第一套像素级自动化测试）

**核心约束**：`Draw` 只接受 `Measure` 返回的 `Fit` 值（字体、字号、样式都封在里面）——
调用方**拿不到单独的字号，也就没法"另起一套"去画**，让反例 #1 那个错误在结构上写不出来。

**全线 GDI+**：因为实测 GDI 的 `DrawText` 在 2560×1440 位图上单次要 9.2ms（小位图只要 0.43ms，差 21 倍）。
这也让"量与画"自然落在同一条路径上。

**测试当场逼出两个没预料到的问题**（这就是自动化测试的价值）：
1. **字号与宽度不是线性关系**（有舍入/hinting），按比例算一次仍溢出 → 改迭代缩小 + 10% 余量；
2. **缩到最小字号仍放不下**时原实现会一直溢出 → 改成逐字截断加省略号（UI 常识）。

**⚠️ 迁移策略（修正）**：**不做一次性大改**。检查后发现现有绘制点**大多本来就是 GDI+ 同源**
（例如 `69-ArcUi.ArcText` 就是 `MeasureString` + `DrawString`，没有 bug），真正的错误只有那处 `TextRenderer`（已修）。
所以 DrawKit 的价值是 **"给新代码用 + 提供统一入口"**，旧代码**按需迁移**，不为迁移而迁移。

---

### 4.1b 原始设想（留档）
新增 `src/16-DrawKit.cs`，把"量了再画"这件事变成**一个 API**，让"度量与绘制不同源"**在结构上不可能发生**：

```csharp
// 现状（危险）：各写各的，量用 A、画用 B，很容易错位
Size sz = TextRenderer.MeasureText(t, f, ...);     // GDI 量
g.DrawString(t, f, br, r, sf);                     // GDI+ 画  ← 不同源

// 重构后（安全）：量返回一个句柄，画只能用它
var fit = DrawKit.Fit(g, text, maxW, pt, fontName); // 内部保证同源
DrawKit.Text(g, fit, rect, color, TextAlign.Center);
```

**收益**：一次修掉这两天反复摔的那个坑，并且**以后不可能再犯**。
**风险**：低（新增层，不改现有行为；逐处替换并对照渲染图验证）。

### 4.2 拆大文件
- `75-SettingsForm.cs` → 按页拆成 `75a/75b/75c/75d`（每页一个 partial）；
- `50-OverlayForm.cs` + `51-Annotate.cs` → 把「标注数据模型（Shape/命中/几何）」独立成 `51a-AnnotModel.cs`，与「绘制」和「交互」分离；
- `61-WheelForm.Draw.cs` → 把「文案表」抽出来（见 4.3）。

**收益**：单文件回到可读规模；改一处不必读四千行。
**风险**：中（机械搬迁，但要逐文件验证渲染一致）。

### 4.3 i18n 校对（✅ 已完成 2026-09-15）

**做法修正**：原计划是"把所有 `Lang.T(zh,en)` 抽成一张对照表"。实测后发现**不值得** ——
`Lang.T` 就地双写已经达到目的（漏翻一眼可见、不用维护 key），抽表是**几百处的大改动**而收益不确定。

**改为**：写了一个**可复跑的检查脚本** `tools\check-i18n.ps1`，自动扫出三类问题：
1. 英文为空、或英文里还残留中文（漏翻）；
2. 同一个中文配了不同的英文（改的时候只改了一处 → 翻译漂移）；
3. 中英长度比异常（只提示，不一定错）。

**实测结果**：**427 条**，**零漏翻、零空值、零不一致**。
标出的"英文过长"都是正常的（"截图"→"Screenshot" 本来就该长）。

以后加文案，跑一次这个脚本就知道有没有漏。

## 五、自动更新（不花钱）与安装包（不做）

### 5.1 自动更新：GitHub Releases API + 自更新器

**完全免费，不需要服务器、不需要签名、不需要任何账号付费。**

```
① 启动时（或每 3 天）GET https://api.github.com/repos/ExpertKT/SnapWheel/releases/latest
   —— 匿名请求，限流 60 次/小时/IP，够用
② 比较 tag_name 与 AppInfo.Version
③ 有新版 → 托盘气泡 + 菜单出现「下载更新 vX.Y.Z」
④ 用户点击 → 下载 zip 到 %TEMP%\SnapWheel-update\
⑤ 解压 → 用 `SnapWheel.exe --apply-update <解压目录>` 启动一个**更新器模式**：
     · 等待当前进程退出
     · 覆盖 exe / 图标 / 说明文件
     · 重新启动主程序并退出自己
⑥ 失败任何一步 → 静默回退，菜单里保留「打开项目主页」手动下载
```

**要点**：
- **不需要证书**：升级是**覆盖已有文件**，不触发 SmartScreen（只有首次下载的新文件会触发，而用户是主动下载的）。
- **国内连不上 GitHub** 是常态 → 检查更新**必须静默失败**，并在设置里给一个开关（默认开）+ 手动「检查更新」菜单项。
- **绿色版可写**：程序放在用户自己的目录里，覆盖自己是允许的。若放在 `Program Files` 且无写权限 → 提示用户手动下载。
- **实现量**：约 300 行（下载 + 解压 + 更新器模式 + 命令行参数）。

**如果你以后想更省心**（可选，不是必须）：换成一个自己的静态域名放版本 JSON，代码几乎不用改（把 URL 抽成常量即可）。但**目前 GitHub 就够了**。

### 5.2 安装包：建议**不做**

| 理由 | 说明 |
|---|---|
| **与核心卖点冲突** | "一个 274KB 的 exe，双击就跑、不写注册表" 是明确写进 README 的卖点。安装包（哪怕 Inno Setup 这种轻量的）也意味着：安装目录、卸载项、开始菜单、可能写注册表 |
| **维护成本真实** | 安装包要跟着每个版本重打、要测升级路径、要处理"装了之后又拿绿色版覆盖"这类脏状态 |
| **Windows 生态已经能覆盖** | 用户想要快捷方式，自己在 exe 上右键"发送到→桌面快捷方式"即可；真想做，我可以在**设置里加一个「创建桌面快捷方式」按钮**（几十行），体验接近安装包，但不留残留 |
| **体积敏感** | 你的目标是轻量化，加安装器会让分发体积从 ~150KB 涨到 ~1MB 以上 |

**替代方案（建议）**：保持 zip 分发 + 在**首次运行引导页**里加一句"想要桌面图标？设置 → 行为 → 创建快捷方式"。成本极低，且完全符合免安装定位。

## 七、0.9.0：传递模式（你的设计）— 第一版已实现

**已落地**：
- `src/93-Carry.cs` —— 传递模式窗口：假光标（画出来的箭头，不是系统光标）+ 吸附的缩略图（带阴影和白边）
- `src/10-Native.cs` —— 新增三个 API：`GetAsyncKeyState`（轮询按键）、`SetCursorPos`、`mouse_event`（模拟拖放）
- `WheelForm.CurrentIndex` —— 对外只读属性，告诉外部"现在停在弧上的是第几张"
- 托盘菜单 →「**传递模式（键盘搬图）**」

**操作**：托盘右键 → 传递模式 → WASD / 方向键移动假光标（Shift 加速）→ Enter / 空格 = 放下 → Esc = 取消

**两个关键设计决定**（都写进了代码注释）：
1. **不用低级键盘钩子**：钩子会插进系统输入链、容易被安全软件盯上、还要求一定卸载；改用定时器 15ms **轮询** `GetAsyncKeyState`，效果一样而代码少得多。
2. **"放下"是真的去动鼠标**：目标程序只认真实的拖放，理解不了"我这边有个假光标"。所以放下的瞬间做的是
   **光标移到起点 → 左键按下 → 分 14 步移过去（模拟人手）→ 左键松开** —— 分步很重要，一步跳过去多数程序不认。

**补充（同一轮做完的三项改进 + 测试）**：
1. **起点改为缩略图的真实屏幕坐标**（`WheelForm.ItemScreenRect`，用 `DrawnRect` + 屏幕坐标换算）——
   原来用轮盘窗口中心，而有些程序要求"按下点确实落在图上"，不满足就不认；
2. **屏幕底部加了操作提示条**（`CarryHintForm`）—— 第一次用的人不可能知道按什么键。
   它单独一个小窗、不抢焦点（`ShowWithoutActivation`），位置贴在光标所在那块屏幕的底部居中；
3. **加了全局热键 `Ctrl+Alt+C`** —— 轮盘是用"不激活"方式显示的（为了不抢别的程序的焦点），
   所以它**收不到键盘输入**，想在轮盘上用键盘进入传递模式只能靠全局热键；
4. **离线测试 `tests/carry-test.cs`（14/14 通过）**：拖放分步插值（起点/终点/单调/越界/步数为 0）、
   缩略图生成（尺寸/居中裁切/**不变形**/null）。
   为了可测，把插值抽成了 `CarryForm.StepPoint`。
   测试过程本身有收获：我一开始按"两侧加黑边"断言，实际实现是**居中裁切填满**（cover，视觉更好），
   **期望写错了而不是代码错了** —— 改成"源图里的正方形在输出里还是正方形"才是对不变形的正确验证。

**第一版的已知限制**（后续迭代）：
- **Esc 取消时缩略图不会"飞回环上"**：现在是直接消失（用户设计里提到飞回动画，还没做）；
- **传递模式中不能换图**：进之前要用滚轮选好（用 A/D 换会和"移动"冲突）；
- 入口只有托盘菜单；轮盘内的键盘选中（方向键选图 + 一个键进入传递）还没做；
- 没有屏幕上的操作提示条（现在靠菜单文案和记忆）；
- 起点的"按下位置"用的是轮盘窗口中心（近似）；某些对落点敏感的程序可能不认，需要时再改精确坐标；
- 与既有拖拽的限制一致：**以管理员权限运行的目标程序收不到**（Windows 的 UIPI 限制）。

### 7.1 原始设计（你的方案，留档）

你的设想很完整，我把它整理成可实现的规格：

```
【阶段 1｜选中】键盘选中一张缩略图（方向键 / 数字键）
【阶段 2｜进入传递模式】
     · 缩略图"提起"（轻微放大 + 阴影），屏幕出现提示条
     · 允许用户自己切屏 / 切窗口（Alt+Tab、鼠标点都行）
【阶段 3｜模拟拖拽】
     · 出现**假光标**（一个小窗口，画一个光标图标，并吸附着缩略图）
     · WASD（或方向键）操控移动，速度可调（Shift = 加速）
     · 按 Esc 取消，缩略图飞回环上
【阶段 4｜落下】
     · 按 Enter / 空格 = 放下
     · 实现方式：把真实光标移到假光标位置 → `mouse_event` 模拟按下/移动/松开
       （这样目标程序会当成一次真正的拖放，兼容性最好）
     · 完成后假光标消失，缩略图按设置决定是否留在环上
```

**技术可行性**：✅ 可行。需要三个新部件：
1. **假光标窗口**（透明置顶小窗，画光标 + 缩略图）；
2. **全局键盘捕获**（传递模式期间用低级键盘钩子 `WH_KEYBOARD_LL`，或注册一组热键）；
3. **拖放模拟**（`SetCursorPos` + `mouse_event`，注意要有"按下 → 分步移动 → 松开"的过程，否则目标程序不认）。

**风险与对策**：
- **假光标与真光标不同步** → 落下时把真光标瞬移到假光标位置（用户会看到光标跳一下，可接受）；
- **目标程序需要真实的拖放过程** → 分步移动（每步 10~20ms），模拟人手速度；
- **管理员窗口收不到** → 与现有拖拽的限制一致（UIA/UIPI），提示用户即可。

**实现量**：约 600~900 行 + 一轮实测调参。你说慢慢磨，我就按这个节奏。
