1 · 核心模型：盒子 vs 便签

C：变量是储物柜

int a = 5;
int b = a;   /* 再租一个柜子，把 5 抄一份放进去 */
b = 7;       /* a 还是 5 —— 两个柜子互不相干 */

int a = 租一个柜子，起名 a。两个柜子，两份数据。

Python：变量是便签纸

a = [1, 2]
b = a
b.append(3)
print(a)     # ?

a = [1,2] = 先造一个箱子，写一张便签「a」贴上去。
b = a = 再写一张便签「b」，贴到同一个箱子上。没有第二个箱子。

类比：C 的 int b = a 是把东西抄一份放进另一个柜子； Python 的 b = a 是在同一个箱子上再贴一张便签。 你透过 b 往箱子里塞东西，透过 a 也看得见 —— 因为是同一个箱子。

所以 b.append(3) 之后 a 也是 [1, 2, 3]。

用你学过的指针说（推荐读） 
/* a = [1,2]    ≈  int *a = make_list(...);  // 造箱子，a 指向它   */
/* b = a        ≈  int *b = a;               // 复制地址，不是内容 */
/* b.append(3)  ≈  list_append(b, 3);        // 改的是同一个箱子  */

Python 的变量几乎都是指针，只是自动帮你解引用，你看不到 *。

这就是它骗人的地方：C 里你写 *b 会被提醒「你在动别人的东西」； Python 里什么提示都没有。

这个类比在第 4 题会骗你。到时候回来再看这句。

2 · 唯一要记的区分：重贴 vs 塞东西

b = b + [3]   # 「b + [3]」造了一个新箱子，把便签 b 撕下来贴到新箱子上
b.append(3)   # 往旧箱子里塞东西，便签没动
操作做什么后果
重新绑定 rebind 把便签撕下来贴到别处 别的便签不受影响
原地修改 mutate 往箱子里塞东西 所有贴着这张便签的都看得见
危险在于：这两件事在代码里看起来一样平常 —— 都是一行，都不报错，后果完全不同。

边界：不是所有箱子都能塞东西

能改（可变）list　dict　set
不能改（不可变）int　str　tuple

b = 7 改不了 7（7 是水泥浇的），Python 只能撕便签重贴。 所以不可变类型表现得像 C 的复制 —— 这是巧合，不是规律。

3 · 一个模型解释四个坑

#坑用这个模型看，它是什么
坑 1 可变默认参数累积 def f(lst=[]) 里那个 [] 在定义时只造了一个箱子， 之后每次调用便签 lst 都贴到同一个箱子上。 而且它能塞东西 → 累积。
坑 2 赋值不是拷贝 就是「便签可以贴很多张」。
坑 3 闭包循环变量全是最后一个值 lambda 捕获的是便签（变量名），不是箱子里的内容。 等它被调用时，便签 i 早被撕到最后一次的箱子上了。
坑 4 is 和 == 不是一回事 is 问「是同一个箱子吗」，== 问「箱子里的东西一样吗」。
漂亮的发现：坑 1 的病因（默认参数在定义时求值）正是坑 3 的解药。 
funcs.append(lambda i=i: i)   # i=i 让 i 在定义时就绑死到当时的箱子
同一条规则，一处害你、一处救你。这说明这些不是零散的注意事项，是一个统一模型的推论。 你要记模型，不要背清单。

第 5 个坑（GIL）性质不同 —— 它是引擎实现层面，不是引用模型。 它在阶段 3~4（网络等待、并发重试）才真正咬到你，到时单独讲。

4 · C → Python 对照表（配类比）

CPython大白话 + 类比
int a[10]a = [0]*10 不是固定长度的柜子，是能自己变长的箱子；还能整段切 a[1:3]
structdict / class / dataclass dict = 贴了名字标签的格子柜；class = 设计图，能造很多箱子并规定它们会做什么
malloc/free自动回收 餐厅有服务员收盘子。但「还有便签贴着的箱子」不会被收 —— 内存泄漏变成引用泄漏
函数指针函数是一等公民 函数本身就是箱子，可以贴便签、可以传参：f = print
char*str（不可变） 字符串是水泥浇的，改不了只能造新的；拼接用 "".join(list)
NULLNone 可以当「没值」，但不要当可变默认参数
错误码异常 出错就「扔」、就近接住；finally 一定执行
头文件 + 声明import 运行时行为，不是编译期
缩进无所谓缩进就是语法 tab 和空格混用直接报错
编译期检查运行时才报错 ← 见下一节

5 · 编译器那条：C 有开关，Python 没有

上表最后一行是语言切换里后果最严重的一条。

C 的编译器替你干了多少活：类型对不对、变量声明了吗、名字拼错了吗、这条分支有返回值吗…… Python 全都不管。

刚才写 00-toolchain-check.py 时，文档字符串里写了 tests\learn，Python 报：

SyntaxWarning: "\l" is an invalid escape sequence.

然后照常运行。

我本来要说「在 C 里这是 error」—— 但我去试了，结果和我预想的不一样：
命令结果
gcc e.c（默认）只有警告，exit 0，照样生成 exe
gcc -Wall -Werror e.cerror，编译失败
所以准确的结论不是「C 报错、Python 警告」，而是：

C 给了你一个开关，能把警告升级成错误（-Wall -Werror）； Python 默认连一个统一的编译器都没有，你得自己把开关装上。

（顺带：上面那个动作本身就是「不确定就做个小实验，比猜快，也比猜可靠」的示范 —— 反例 #10。）

阶段 2 整章都在干「装开关」这件事：类型注解 + mypy/pyright + ruff + pytest。

它们不是「好习惯」，它们是在还债 —— 还 C 的编译器替你付掉、而 Python 让你自己付的那笔债。

6 · 练习：先预测，再运行

tests/learn/stage1-predict.py 出题，5 道，每题是一个能跑的迷你程序。

规则只有一条：先写下预测，再运行。

它会拒绝运行，直到你写出 tests/learn/stage1-predictions.md（至少 400 字）。 闸门已验证：没文件 → 拒绝并 exit 1；有文件 → 正常出题。

为什么要有闸门？ 这是反例 #1 的教训用在你自己身上。

反例 #1 说：靠「记得别写错」不可靠，好的设计让错误写不出来。

学习一样。你现在觉得「我知道 b.append 会改到 a」—— 那是看到答案之后的错觉。 把预测写下来、跑出来、发现错了，那个错才真的属于你。
所以闸门不是刁难，是把「先预测」变成你绕不过去的结构。

流程

  1. 写 stage1-predictions.md：5 题各写你预测的完整输出 + 一句话说为什么
  2. python stage1-predict.py 1 逐题跑（1~5）
  3. 在同一文件里写差异分析：哪里错了、为什么错、现在你怎么理解
前提：先不要读 docs/LEARNING.md 的 §1.2，那里有答案。 等你写完预测、跑完、分析完再回去对照 —— 那时它是答案对照表，不是剧透。

7 · 六个「为什么」

我要你的话，不要术语堆砌。

  1. 第 1 题里 b = b + [3] 和 d.append(3) 长得几乎一样，为什么结果不同？用「箱子/便签」讲。
  2. 第 2 题两个函数都在「改」lst，为什么只有一个真改到了外面？
  3. 第 3 题改成 tags=None + if tags is None: tags = {} 就好了。 为什么这个改法有效？它和第 5 题 B 版的 lambda i=i 是同一个机制吗？
  4. 第 4 题里 1000 和 1000 是「同一个箱子」，但 1000 和 int("1000") 不是。同一个数字，为什么「是不是同一个箱子」会不一样？ 那么 —— 什么时候才该用 is？
  5. 第 5 题 B 版修好了。为什么说「坑 1 的病因正是坑 5 的解药」？
  6. （C 对照题） 用指针说：b = a（a 是列表）最接近 C 里哪一句？ b.append(3) 又最接近哪一句？ Python 把 * 和解引用都藏起来了 —— 这让你更容易出错，还是更不容易？说出理由。

第 6 题没有标准答案。我要看你怎么想。
