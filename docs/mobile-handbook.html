你不需要先学很多 C# 才能看懂这个项目。下面这些是够用的映射，遇到新的再回来查。

2 · 我的项目长什么样

一句话：Windows 上的截图工具。截完图不弹保存框，图直接变成屏幕角上一张缩略图（排成一段圆弧），要用的时候把缩略图拖进任何程序就发出去了。

三条主流程（整个项目就围绕这三条线）：

① 截图线：热键 → 全屏浮层 → 拖框选 → 标注/取字 → 确认
                                    ↓ 合成成一张位图
② 收纳线：位图 → 存进"轮盘"（内存里的列表）→ 屏幕角落的圆弧上排开
                                    ↓
③ 用图线：缩略图 → 拖出去（OLE 拖放）→ 目标程序收到文件或位图

技术栈：C# / .NET Framework 4.0 / WinForms，约 2 万行、38 个源文件。所有界面全部自己画（没有 UI 框架、没有一张图片资源），编译用 Windows 自带的编译器，零第三方依赖，产物是单个约 300KB 的 exe。

3 · 七个「为什么」

代码能看出"怎么做"，看不出"为什么"。这七条是项目里最难被外人看懂的部分。

3.1 为什么窗口要自己画，不用系统控件？

因为要真透明。Windows 上想要"只有圆弧和缩略图、其余完全透明"的窗口，必须用分层窗口。而分层窗口不能承载普通控件 —— 控件的绘制不走分层通道。

代价：按钮、圆角、阴影、图标、文字全得自己画。收益：视觉完全可控。

3.2 为什么毛玻璃要自己抓屏，不用系统效果？

两个原因：① 分层窗口用不了系统毛玻璃；② 系统效果会给整个窗口矩形蒙一层灰，而我们要"只糊面板内部、边缘干净"。

做法：后台线程每 3.5 秒抓一次屏幕 → 模糊 → 裁进面板形状。抓屏时给窗口打标记，保证不会拍到自己。

3.3 为什么要有「分层缓存 + 签名」？

一帧如果每次都把所有矢量图形重画，要 12.7ms（量出来的）。做法：把画面分成三层（环/缩略图/控件），每层缓存成位图，每帧只贴图。

但贴图有个前提：缓存必须还有效。于是给每层算一个签名（由"这一层依赖的所有状态"混合而成：悬停项、偏移量、缩放、颜色…）。

规则：任何参与绘制的状态都必须进签名，否则画面会卡在旧状态（我们真踩过，见 §4.6）。
3.4 为什么偏移量要有两个变量（当前值 / 目标值）？

_targetOffset = 目标（滚轮一滚就变，代表用户意图）
_offset = 当前值（每帧向目标靠近一小步，代表动画）

分开的好处：意图立刻记录、画面平滑跟上。所有动画系统都是这个套路（C 里写游戏循环也一样）。

3.5 为什么要统一用「屏幕坐标」？

因为要跨多显示器工作。统一用虚拟屏幕坐标的好处是"算一次到处能用"；代价是任何相对坐标都要显式转换 —— 忘记转换就会出现"面板跑到副屏去了"（我们踩过）。

3.6 为什么设置窗口翻页要用「位图滑动」？

因为控件在翻页时要重排 + 重绘，会闪、会掉帧。做法：动画期间把两页各渲染成位图，滑动位图；动画结束再切回真实控件。

通用套路：动画期间用位图，静止时用控件。

3.7 为什么「拖出去」是复制语义？

拖放调用用的是"复制"效果 —— 目标程序拿到的是副本，所以环上那份应该留着（想再拖一次、或拖给第二个窗口都要用）。

我们曾经在拖出成功后把图从环上删掉（把复制当成了移动），于是"拖一次就没了"。见 §4.3。

4 · 反例库：我们踩过的 10 个坑

这是整册最有价值的部分。每条都是真实的：有症状、有日志、有数据。你不用再走一遍，但要能讲出"为什么会这样"。

4.1度量与绘制不同源 —— 同一个坑摔了四次

症状：文字/图形的位置和它的边框、命中区域对不上，或者被裁掉一半。

根因：测量用一套参数，绘制用另一套。四次分别是：

  1. 用 GDI+ 的方式量宽度、却用另一种方式画 → 实际更宽 → 右边缘被切；
  2. 格子按 20pt 字号算，而表情的行高远大于字号 → 被裁；
  3. 量框用中文字体、画的时候用符号字体 → 两个字体宽高不同 → 错位；同时锚点不一致（框按左上角、画按中心）→ 差半个字；
  4. GDI 与 GDI+ 混用：用 GDI 画，却期望它响应 GDI+ 的旋转/平移变换 —— GDI 完全不理会，于是预览正常、一合成到成品图就跑到图外。
正确做法：测量和绘制必须同一条 API 路径；锚点必须一致；字体必须一致。更工程化的做法是把这几件事封装成一个函数，让调用方不可能写错。
这条的普适教训：很多 bug 不是"写错了"，而是"约定没有强制"。好的设计让错误写不出来。
4.2不要用字符串片段做批量替换的锚点

症状：批量改文案后，编译报错一片，字符串被劈成两半。

根因：把 " 张"、" 行" 这种片段当查找目标，而它们是更大字符串的一部分。

正确做法：用完整字符串做锚点；批量改完必须编译验证；先确认目标唯一。

4.3语义搞错：把「复制」当成了「移动」

症状：拖出去的图从环上消失了，不能再拖第二次。

根因：拖放用的是复制效果，但成功后代码把图从列表里删了。

正确做法：先想清楚操作的语义（复制？移动？），再写代码。

4.4状态用属性临时保存，嵌套时丢失

症状：打开设置窗口，它跑到了轮盘下面（以为没打开）；截图界面也在下层。

根因：为了让轮盘让位，代码临时把它设为非置顶，结束再恢复。但多处嵌套（截图时又打开设置）→ 恢复时拿到的是中间态 → 状态永久丢失。

正确做法：用计数 / 引用计数：第一个进入时保存原值、最后一个离开时恢复。这是"可嵌套资源管理"的通用模式（C 里做锁、做引用计数同理）。
附加教训：改这个时我只抑制了"重新置顶"，却忘了它本来就还在顶层 —— 没修好还创造新 bug。改状态机前，先把它所有状态和转换画出来。
4.5显示值用错变量：当前值 vs 目标值

症状：滚轮滚动时，"第几张 / 共几张"的数字不变。

根因：数字用了当前动画值（要等动画追上去才更新），而用户期望"滚轮一动就变" → 应该用目标值。

正确做法：区分"意图"和"呈现"。反映用户操作的显示用目标值；反映动画进度的用当前值。

4.6新状态没进缓存签名

症状：新加的动画完全不动，或画面卡在旧状态。

根因：项目用"层签名"决定缓存是否有效（§3.3）。新增了参与绘制的状态，却没把它混进签名 → 系统以为缓存还有效 → 一直贴旧图。

正确做法：任何参与绘制的状态都必须进签名 —— 把它当成"改绘制代码的检查清单第一项"。

4.7按中文宽度设计的布局，换英文就溢出

症状：做成多语言后，英文一行挤成一长串被裁；提示文字压住了别的元素。

根因：布局宽度是按中文字符数估的，英文同义句往往长 50%~100%。

正确做法：① 不按"字符数"算宽度，按实测宽度（同 §4.1）；② 有些控件不会自动折行，要在文案里手工插换行；③ 设计时就用最长的语言试一遍。
4.8构建脚本的编码：BOM 不是可选项

症状：改完构建脚本，突然报一堆语法错误、中文全变乱码。

根因：PowerShell 对没有 BOM 的 UTF-8 脚本会按系统本地编码解释 → 中文全乱 → 语法崩。

正确做法：写回脚本文件时必须带 BOM。这条很小，但我把能跑的构建脚本搞坏了两次，都靠版本控制才恢复。

4.9不要用「解析输出」判断成败

症状：脚本里写"编译成功就提交"，结果连续两次把编译不过的版本推了上去。

根因：① 判断写了正则但没转义元字符，匹配失败；② 改成字符串包含也失败 —— 因为那个构建脚本用只输出到屏幕的方式打印，不进管道，变量一直是空的。

正确做法：用"产物是否存在且合理"判断（文件在不在、大小对不对），或者用退出码。不要解析给人看的输出。

附带教训：先编译、再提交。我把顺序写反了两次。

4.10先测量，再优化 —— 方法论中的方法论

症状：比例面板展开动画卡顿。我猜了三个原因、改了三轮，都没解决。

实测之后：

  • 我以为的元凶（每帧重贴整张 2560×1440 底图）实测是 0.31ms —— 根本无关；
  • 真正的数据：全屏重绘 22.2ms/帧（≈45fps），局部重绘降到 13.5ms —— 这才是"帧率低"的确切原因。
正确做法：① 先加计时，拿到分段数据；② 按数据改，不按直觉改；③ 改完再测一次验证。
一句话记住：没有测量就没有优化，只有猜测。 我在这上面白烧了大量时间和额度。

5 · 学习路线（7 个阶段）

每阶段都是「原理 → 看真实代码 → 看反例 → 自己动手 → 验收」。练习写在 tests/learn/。

阶段 1｜一个程序是怎么"活"起来的

原理：程序入口、事件循环、消息、回调。C 里是 main + while + 函数指针；Windows 程序是 WinMain + 消息循环 + 窗口过程回调。

代码：90-App.cs（入口与托盘）、10-Native.cs（怎么声明系统调用）。

动手：写一个 50 行的窗口程序，点一下就换标题。

验收：能解释"我点了按钮之后，代码从哪一行跳到哪一行"。

阶段 2｜数据怎么组织（从结构体到类）

原理：结构体→类；函数指针→委托/事件；malloc/free→GC 与生命周期；封装到底解决什么问题。

代码：25-Store、30-Wheel、27-Undo。

反例：§4.3（语义不清导致逻辑错误）。

动手：用 C 写一个"能存 N 条、能删、能撤销"的小程序（自己写，不看项目代码），写完再对照项目看它怎么做得更好。

验收：能说清"为什么撤销用引用计数而不是拷贝"。

阶段 3｜画到屏幕上（核心阶段）

原理：坐标系、绘制原语、双缓冲（为什么需要）、裁剪、抗锯齿、字体度量。

代码：15-Gfx、40-RoundButton（最小完整控件）、61-….Draw。

反例：§4.1（摔了四次的坑）+ §4.7。

动手：写一个自绘按钮：悬停变色、按下变暗、文字真正居中（用测得的尺寸算）。写完截图放大，用尺子量是否真居中。

验收：能讲出"为什么测量和绘制必须同源"，并举出一个会出错的例子。

阶段 4｜交互（命中、状态、焦点）

原理：命中测试、状态机、焦点与激活、窗口层级（Z 序）。

代码：64-….Input、51-….Annotate（选中/拖动/缩放）。

反例：§4.4（状态嵌套丢失）+ §4.5。

动手：给阶段 3 的按钮加上拖动、缩放、删除、撤销，再加一个动画过渡。

验收：能在纸上画出一个对象的所有状态和转换。

阶段 5｜让程序跑得快且不卡（性能工程）

原理：帧预算（60fps = 16.7ms）、缓存、失效与签名、测量方法。

代码：66-….Layers、05-Err（帧耗时统计）。

反例：§4.6 + §4.10（先测量再优化）。

动手：给自己阶段 4 的程序加"帧耗时打印"，然后故意制造卡顿，用数据找出原因并修掉。

验收：能独立完成"测量 → 定位 → 优化 → 复测"整套流程。

阶段 6｜工程化（从"能跑"到"能维护"）

原理：分层与依赖方向、构建脚本、测试的价值、配置兼容、多语言、发布流程。

代码：tools/build.ps1、tests/、35-Settings（配置迁移）、14-Lang。

反例：§4.2、§4.8、§4.9。

动手：给自己的程序加：一键构建脚本、3 个自动化测试、一个配置文件（且旧配置能读）。

验收：能解释"为什么测试值得写"，并举出你自己代码里一个"当初写测试能省几小时"的例子。

阶段 7｜毕业设计：独立完成一个小工具

范围 200~800 行，从需求到发布全流程：自己定需求、自己设计、自己写、自己测、自己打包、写 README。

建议题材：和 SnapWheel 同类但不同 —— 剪贴板历史、颜色拾取器、窗口置顶工具。

AI 的角色：审阅者，只在你卡住时给方向，不写代码。

验收：你能完整讲一遍 —— 为什么这么分层、最大的技术问题是什么、怎么解决的、如果重做会改哪里。

6 · 术语速查

词一句话解释
分层窗口一种支持"整窗按像素透明"的窗口，代价是不能放普通控件，一切自己画
双缓冲先在内存里画好一整张，再一次性贴到屏幕，避免闪烁
裁剪（Clip）限制"只能画在某块区域里"，超出部分不画
脏区需要重绘的那一小块区域。只重绘脏区能大幅省时间
帧预算60fps 意味着每帧只有 16.7ms，所有绘制必须在此之内完成
缓存失效缓存的内容过时了、不能再用。需要一个机制判断"还能不能用"
签名把一组状态压缩成一个数字，用它快速判断"缓存是否需要重建"
命中测试判断"鼠标点在了哪个对象上"
状态机用"当前处于哪个状态"来决定"该响应什么"。状态多时画成图最不容易错
Z 序窗口的前后层叠顺序
置顶（TopMost）让窗口始终显示在其它窗口之上
焦点键盘输入会送到"拥有焦点"的窗口
激活把某窗口提到前台并给它焦点
委托 / 事件C 里函数指针的升级版：可以带上下文，事件是"一对多"
闭包一个函数 + 它记住的外部变量。C 里要手动传结构体才能做到
partial 类一个类写在多个文件里，编译时合并 —— 用来拆分超大文件
DPI 缩放高分屏上按比例放大界面。必须统一入口，否则各处尺寸会打架
OLE 拖放Windows 标准的"拖文件到别的程序"机制
OCR从图片里识别文字
回归（regression）改 A 的时候把原本好的 B 弄坏了

7 · 通用套路速查卡

这些是跨语言、跨项目都成立的经验。忘了就回来翻。

关于正确性

  • 量了再画，且两件事必须同源（§4.1）
  • 让错误写不出来，比"记得别写错"可靠得多（§4.1 的封装）
  • 先想清语义（复制还是移动？谁拥有这块内存？）再写代码（§4.3）
  • 状态要么完整，要么不存在 —— 半途状态最危险（§4.4）

关于性能

  • 先测量，再优化（§4.10）—— 这是最省钱的一条
  • 只重绘变了的那一块（脏区思维）
  • 缓存 + 一个明确的失效判据（§4.6：判据漏了就会卡住）
  • 动画期间用位图，静止时用控件（§3.6）

关于可维护性

  • 可嵌套的资源管理要用计数，不要用"记住原值再恢复"（§4.4）
  • 能自己说出"我哪里慢、哪里错了" —— 日志与计时是一等功能（05-Err）
  • 把平台相关的调用集中到一处（10-Native）
  • 构建脚本是项目的一部分，要能一键复现

关于工作方式

  • 改完就编译验证，别攒着（§4.9：我曾把编译不过的版本推上去两次）
  • 用"产物"验证，不要解析给人看的输出（§4.9）
  • 批量替换用完整锚点，改完必编译（§4.2）
  • 不确定就做个小实验 —— 这比争论和猜测都快（§4.10）
